Dimension details
2 Integration Surface All 3 signals via native OTLP/gRPC; OTLP is the only tracing path; vendor metric backends remain co-equal ▶

What we observed

Traefik v3.7.1 pushes all three signals natively via OTLP/gRPC directly to the OTel Collector — no sidecar, bridge, or adapter required. Traces flow through the github.com/traefik/traefik instrumentation scope. Metrics arrive via a dual pipeline: OTLP/gRPC push every 10 s and a Prometheus scrape of port 9100 every 15 s. Access logs require enabling experimental.otlpLogs: true and produce 72 records with full trace context. All three signals required explicit opt-in via project-specific Helm values — none default to OTLP out of the box.

What's working well

  • Jaeger and Zipkin were completely removed in v3.0 — OTLP is now the only tracing export path, representing a genuine architectural commitment to OpenTelemetry.
  • The OTel Go SDK is embedded directly in the Traefik binary; all three signals push natively via OTLP/gRPC without requiring any sidecar or protocol adapter.

Opportunities

Standard env var support — Documenting support for OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_EXPORTER_OTLP_PROTOCOL would allow operators to configure Traefik using the same env var patterns as any other OTel-instrumented service, reducing onboarding friction.
Graduate OTLP log export — The experimental.otlpLogs: true feature gate makes log export the only signal still gated. Graduating it to stable would complete the full three-signal OTLP story and remove the need for operator workarounds.

Checklist

  • ✓ All three signals (traces, metrics, logs) flow via OTLP/gRPC natively
  • ✓ No sidecar, bridge, or protocol adapter required — Traefik pushes directly to the OTel Collector
  • ✗ OTLP log export still behind experimental.otlpLogs: true feature gate
  • ✗ OTEL_EXPORTER_OTLP_ENDPOINT not documented as supported; endpoint requires project-specific Helm flags
1 Semantic Conventions Traefik spans use current OTel HTTP semconv; proprietary traefik_* metrics and PascalCase log attributes fragment cross-signal correlation ▶

What we observed

Traefik's own instrumentation scope (github.com/traefik/traefik) exclusively uses current, stable OTel HTTP semantic conventions on spans: http.request.method, http.response.status_code, url.full, url.path, server.address, client.address, network.protocol.version, user_agent.original. Schema URLs (https://opentelemetry.io/schemas/1.40.0) are present on all three signals. However, the 13-metric traefik_* family uses non-OTel attribute keys (code, method, protocol), and access log attributes use proprietary PascalCase names (RequestMethod, DownstreamStatus, RequestPath) rather than OTel semconv equivalents.

What's working well

  • Traefik's own tracer exclusively uses current, stable OTel HTTP semconv — attributes like http.request.method and http.response.status_code are correct on every span.
  • The two OTel-named metrics (http.server.request.duration and http.client.request.duration) are correctly named and use current OTel attribute keys. Schema URLs are present on all three signals.

Opportunities

Align proprietary metric attribute keys with OTel semconv — The traefik_* metric family uses code, method, protocol where OTel semconv defines http.response.status_code, http.request.method, network.protocol.version. Adopting OTel keys would enable cross-signal correlation without attribute mapping.
Adopt OTel attribute naming in access logs — Log attributes currently use Traefik-proprietary PascalCase names (RequestMethod, DownstreamStatus, ClientAddr). Mapping these to their OTel equivalents would make the concept of "HTTP method" consistent across traces, metrics, and logs — currently it has three different names.
2 Resource Attributes & Configuration Rich native resource attributes across all signals; service.name consistent; OTEL_SERVICE_NAME undocumented ▶

What we observed

Traefik v3.7.1 emits a rich set of native resource attributes via the OTel Go SDK's resource.New(...) call: service.name=traefik, service.version=3.7.1, telemetry.sdk.name=opentelemetry, telemetry.sdk.language=go, telemetry.sdk.version=1.43.0, plus host.name, os.type, os.description, and a full process.* attribute set. Traefik's built-in Kubernetes detector (k8sdetector.go) natively emits k8s.namespace.name, k8s.pod.uid, and k8s.pod.name without requiring the OTel Collector's k8sattributes processor. service.name and service.version are identical across all three signals and both metrics collection methods.

What's working well

  • service.name and service.version are stable and consistent across traces, OTLP metrics, Prometheus-scraped metrics, and logs — no identity misplacement on span attributes.
  • The built-in Kubernetes resource detector natively emits k8s.namespace.name, k8s.pod.uid, and k8s.pod.name — Kubernetes identity is available even without OTel Collector enrichment.

Opportunities

Document OTEL_SERVICE_NAME override behavior — While OTEL_SERVICE_NAME is functionally supported via the OTel Go SDK's resource.WithFromEnv() detector, it is not documented in Traefik's reference. Adding a note clarifying the precedence order between tracing.serviceName, tracing.resourceAttributes, and OTEL_RESOURCE_ATTRIBUTES would help operators managing multi-tenant deployments.
Add service.instance.id for multi-replica deployments — For deployments running multiple Traefik replicas, emitting service.instance.id natively (e.g., using the pod name) would allow operators to distinguish per-replica telemetry without relying on collector enrichment.
2 Trace Modeling & Context Propagation W3C Trace Context is default; correct span kinds; coherent GET→ReverseProxy→upstream chain confirmed ▶

What we observed

W3C Trace Context (traceparent) is the default propagator, confirmed by observed trace data where an external traceparent header was extracted and honored. Trace 4bf92f3577b34da6a3ce929d0e0e4736 (40 spans) shows 5 Traefik GET (SERVER) spans correctly parented to an external span ID not present in the collected data. The ReverseProxy (CLIENT) span injects context into upstream requests, causing the backend to produce SERVER spans within the same trace. Span kinds are intentional: SERVER for entry points (102 spans), CLIENT for outbound proxy calls (24 spans), INTERNAL for middleware (117 spans).

What's working well

  • The complete proxied request chain is coherent: GET (SERVER) → ReverseProxy (CLIENT) → upstream GET / (SERVER), with correct parent-child relationships confirmed across 20 multi-span traces.
  • The 54 single-span traces are all for /ping or /metrics — legitimate terminal endpoints at Traefik itself, not trace fragmentation.

Opportunities

Add router and service context to trace spans — Currently, trace spans carry an entry_point attribute but not the matched router or service name. Adding these as span attributes would allow operators to identify which Traefik routing rule matched a request directly from trace data, without cross-referencing access logs.
Use span events for retry and error context — The 3 error spans for 404 upstream responses correctly set status.code=2 but carry no status message. Adding span events for upstream retries, circuit breaker state changes, or TLS handshake details would make the trace data more actionable for debugging.
2 Multi-Signal Observability All 3 signals flowing; 100% log-trace correlation; 6 shared attribute keys enable metric→trace→log pivot ▶

What we observed

All three signals are first-class OTLP outputs. Trace context is automatically injected into every access-log record: 24 of 24 log records (100%) carry a non-zero traceId and spanId, with 20 distinct trace IDs confirmed to appear in both traces.jsonl and logs.jsonl. Six shared attribute keys exist between traces and OTel metrics: http.request.method, http.response.status_code, network.protocol.version, server.address, server.port, url.scheme. The entrypoint dimension also aligns across metrics and the entry_point span attribute.

What's working well

  • Automatic trace-to-log correlation at 100% coverage — every access-log record carries matching traceId and spanId, enabling metric → trace → log pivoting without manual bridging or timestamp alignment.
  • Six shared OTel semantic convention attribute keys between traces and metrics allow filtering spans by the same dimensions used for metric anomaly detection.

Opportunities

Document the cross-signal investigative workflow — The metric → trace → log pivot is technically possible but undocumented. A guide showing how to go from an elevated http.server.request.duration metric to a correlated trace and then to the matching access-log record would make this capability discoverable.
Add router/service dimensions to OTel-native metrics — The OTel-semconv metric http.server.request.duration does not carry router or service labels — these dimensions are only available in the legacy traefik_router_* Prometheus-format metrics. Bridging this gap would make the OTel-native metric path fully equivalent for SLO use cases.
1 Audience & Signal Quality Metrics are SLO-ready; ReverseProxy span name is internal; severity mismatch bug in logs; router context absent from spans ▶

What we observed

Traefik's metrics signal is the strongest: three layers of granularity (entrypoint → router → service) with SLO-relevant metrics like traefik_entrypoint_request_duration_seconds, traefik_router_requests_total, and the OTel-native http.server.request.duration. However, trace span names have usability gaps: ReverseProxy is an internal Traefik component name, and bare GET spans lack routing context. A severity mismatch bug affects all 24 access-log records: OTel severityText=info while the JSON body contains "level":"panic" — alerting systems relying on OTel severity levels would be misled. Router and service context is entirely absent from trace spans.

What's working well

  • The metrics signal is genuinely operator-focused and SLO-ready: three granularity layers (entrypoint, router, service) with well-controlled label cardinality (code, entrypoint, method, router, service).
  • The OTel-native http.server.request.duration and http.client.request.duration metrics correctly implement OTel HTTP semantic conventions and are immediately usable for RED method dashboards.

Opportunities

Fix the log severity mismatch bug — All 24 access-log records have OTel severityText=info (severityNumber=9) while the embedded JSON body contains "level":"panic". This is a production-quality defect that would cause severity-based alerting rules to silently miss critical events. Aligning the OTel envelope severity with the actual log level is a high-impact, low-effort fix.
Rename ReverseProxy span and add routing context — The ReverseProxy span name exposes an internal Traefik component name. Renaming it to something like proxy or upstream.request and adding traefik.router.name and traefik.service.name attributes to entry-point spans would make trace data immediately interpretable by operators unfamiliar with Traefik internals.
2 Stability & Change Management Schema URLs on all signals; versioned migration guide with breaking-change callouts; traces scope version is unknown ▶

What we observed

Schema URLs (https://opentelemetry.io/schemas/1.40.0) are present on all three signals. Breaking telemetry changes are consistently documented in a versioned migration guide with explicit "Migration Required" and "Impact" sections. Examples include: the traefik_tls_certs_not_after_milliseconds → traefik_tls_certs_not_after_seconds rename (v3.5.4), the request duration unit change from milliseconds to seconds (v3.3.4), and the traceVerbosity default change that reduced span count (v3.5.0). Official Grafana dashboards create accountability for metric stability. However, the traces instrumentation scope version is unknown while the metrics scope correctly carries v3.7.1.

What's working well

  • Breaking telemetry changes are proactively communicated with "Migration Required" sections, old/new value comparisons, and migration steps — the v3.5.0 traceVerbosity change explicitly warned users that fewer spans would be produced.
  • Official Grafana dashboards are maintained and published, creating accountability for metric stability and giving operators a reference implementation for monitoring Traefik.

Opportunities

Add per-signal stability labels — Users currently cannot tell which telemetry signals are safe to build long-lived SLOs on. Adding stability markers (e.g., "stable", "experimental") to individual metrics and spans in the reference documentation would help operators make informed decisions about which signals to depend on.
Fix traces instrumentation scope version — The traces instrumentation scope version is unknown while the metrics scope correctly carries v3.7.1. Setting the trace scope version to the Traefik release version would allow consumers to correlate telemetry shape with a specific release and detect instrumentation changes automatically.
Key takeaways

● Strengths

  • Zero-adapter OTLP pipeline — All three signals push natively via OTLP/gRPC; Jaeger and Zipkin removed in v3.0; the OTel Go SDK is embedded directly in the binary
  • 100% log-trace correlation — Every access-log record automatically carries matching traceId and spanId; 20 trace IDs confirmed across both signals
  • Proactive change management — Breaking telemetry changes documented with Migration Required sections; schema URLs on all signals; official Grafana dashboards create metric stability accountability

● Priority improvements

  • Fix log severity mismatch — All 24 access-log records show severityText=info while the JSON body contains "level":"panic" — a production defect that would cause alerting systems to miss critical events
  • Align semconv across signals — "HTTP method" currently has three names: http.request.method (traces), method (metrics), RequestMethod (logs); aligning to OTel semconv would enable true cross-signal correlation
  • Add routing context to spans — Router and service name are absent from trace spans; adding traefik.router.name and traefik.service.name would make traces independently useful without cross-referencing logs
  • Graduate OTLP log export — The experimental.otlpLogs feature gate is the only remaining barrier to a fully stable three-signal OTLP story

● Notable observations

  • Dual metrics pipeline ambiguity — Traefik simultaneously pushes OTLP metrics (with http.server.request.duration) and exposes a Prometheus scrape endpoint (with traefik_* metrics); no documentation guides users on which to use or how to avoid double-counting
  • Native Kubernetes resource detection — Traefik natively detects k8s.namespace.name, k8s.pod.uid, and k8s.pod.name via its own k8sdetector.go — Kubernetes identity is available even without OTel Collector enrichment
  • Probe traffic noise in traces — Kubernetes liveness probe traffic (/ping) and Prometheus scrape traffic (/metrics) are included in traces by default, producing 54 single-span traces with no operational value; sampling or filtering guidance would reduce noise
