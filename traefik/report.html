Dimension details
2 Integration Surface OTLP is the sole tracing backend in v3; all three signals flow natively via OTLP gRPC. Prometheus metrics remain co-equal default; OTLP logs are experimental. ▶

What we observed

Traefik v3 uses the OTel Go SDK directly and emits spans via otlptracegrpc natively — no adapters or sidecars needed. All three signals (traces, metrics, logs) flow via OTLP gRPC to the OTel Collector. Tracing is fully native with the sole backend being OTLP since v3.0 removed Jaeger, Zipcon, and all legacy exporters. Metrics run a dual pipeline: OTLP push is opt-in while Prometheus is the Helm default. Logs require the --experimental.otlpLogs=true feature gate. Configuration uses Traefik-native CLI flags rather than standard OTEL_EXPORTER_OTLP_ENDPOINT or OTEL_SERVICE_NAME env vars.

What's working well

  • OTLP is the sole tracing backend in v3 — Jaeger, Zipcon, Instana, and all legacy exporters were removed in v3.0, making OTLP the unambiguous standard.
  • All three signals flow natively via OTLP gRPC to a standard OTel Collector — no adapters, no sidecars, no bridges required.

Opportunities

Adopt standard OTEL_* env vars — Supporting OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_SERVICE_NAME as primary configuration surfaces would bring Traefik in line with the broader OTel ecosystem and simplify deployment in OTel-aware environments.
Graduate OTLP logs to stable — The --experimental.otlpLogs=true feature gate works reliably in practice. Graduating it to stable would complete the fully-native three-signal story and make Prometheus the clearly-secondary metrics path.

Checklist

  • ✓ OTLP is the sole tracing backend in v3.x — all legacy exporters removed
  • ✓ No adapters or sidecars required — direct OTLP gRPC push to Collector
  • ✗ OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_SERVICE_NAME not supported as primary config
  • ✗ Prometheus metrics is the Helm default; OTLP metrics requires explicit opt-in
1 Semantic Conventions Traefik's own spans use fully current OTel HTTP semconv. Dual metric naming paradigms and proprietary log attributes prevent Level 2. ▶

What we observed

Traefik's own spans use fully current OTel HTTP semantic conventions — attributes like http.request.method, http.response.status_code, url.scheme, server.address, and network.protocol.version appear correctly on 98 spans. Schema URLs (https://opentelemetry.io/schemas/1.40.0) are present on all three signals. However, Traefik's Prometheus-style metrics use non-OTel attribute keys (method, code, protocol instead of OTel semconv equivalents), log attributes are entirely proprietary (ClientAddr, DownstreamStatus, RouterName), and deprecated attributes from the backend's Node.js auto-instrumentation appear within the same traces.

What's working well

  • Traefik's own instrumentation scope uses fully current OTel HTTP semconv — no deprecated http.method or http.status_code on Traefik-emitted spans (those only appear on the backend's Node.js auto-instrumentation).
  • OTel semconv metrics http.server.request.duration and http.client.request.duration use correct current attribute keys, and schema URL 1.40.0 is present on all three signals.

Opportunities

Align Traefik metric attribute keys with OTel semconv — The traefik_* metrics currently use abbreviated labels (method, code, protocol) instead of OTel semconv keys (http.request.method, http.response.status_code, url.scheme). Aligning these would enable cross-signal correlation without project-specific knowledge.
Adopt OTel semconv for log attributes — Access log attributes like ClientAddr, DownstreamStatus, and RequestMethod could map to OTel semconv equivalents (client.address, http.response.status_code, http.request.method), enabling log-based queries that work identically across all OTel-instrumented services.
2 Resource Attributes & Configuration service.name and service.version stable and consistent across all three signals. Native Kubernetes attribute auto-detection. OTEL_SERVICE_NAME undocumented. ▶

What we observed

Traefik v3.7.0 uses the OTel Go SDK (v1.43.0) and emits a rich set of resource attributes natively via OTLP for all three signals. service.name=traefik and service.version=3.7.0 are stable and identical across traces, metrics, and logs. Process and OS attributes (process.pid, process.executable.name, os.type, os.description) are emitted automatically. When running in Kubernetes, k8s.namespace.name, k8s.pod.uid, and k8s.pod.name are auto-detected natively. The OTEL_RESOURCE_ATTRIBUTES env var is explicitly documented and supported.

What's working well

  • service.name and service.version are stable and consistent across all three signals — traces, metrics, and logs all report service.name=traefik and service.version=3.7.0.
  • Native Kubernetes attribute auto-detection: k8s.namespace.name, k8s.pod.uid, and k8s.pod.name are populated without any Collector-side enrichment.

Opportunities

Document OTEL_SERVICE_NAME behavior — The relationship between OTEL_SERVICE_NAME and the split tracing.serviceName / metrics.otlp.serviceName config options is undocumented. Clarifying precedence and ideally converging on OTEL_SERVICE_NAME as the standard env var would reduce operator confusion in multi-signal deployments.
Emit service.instance.id natively — service.instance.id is absent from traces and logs natively. In multi-replica deployments, distinguishing telemetry from individual Traefik pods requires relying on pipeline-enriched k8s.pod.name rather than a first-class OTel identity attribute.
2 Trace Modeling & Context Propagation W3C Trace Context extraction and injection confirmed. Coherent SERVER→CLIENT→SERVER→INTERNAL topology. No span events or architectural trace modeling docs. ▶

What we observed

311 spans across 142 distinct traces were captured. Multi-span traces (20 traces with 7-40 spans each) show a coherent SERVER→CLIENT→SERVER→INTERNAL topology: entry-point GET spans (SERVER kind) spawn ReverseProxy CLIENT spans, which parent backend SERVER spans, which parent Express middleware INTERNAL spans. The 40-span fan-out trace confirms correct W3C Trace Context extraction from an incoming traceparent header — Traefik SERVER spans are correctly parented to an external span ID not present in the dataset. Single-span traces are exclusively Kubernetes liveness probes (/ping) and Prometheus scrapes (/metrics), not user-traffic fragmentation.

What's working well

  • W3C Trace Context propagation is correct and complete — both extraction from inbound requests and injection into outbound proxy calls are verified by a 40-span trace that continues an externally-initiated trace ID across 5 parallel backend calls.
  • Span kinds are intentional and correct: SERVER at entry points, CLIENT for proxy calls, INTERNAL for middleware — and this topology is validated by integration tests (TestOpenTelemetryRetry, TestOpenTelemetryAuth, TestOpenTelemetryRateLimit).

Opportunities

Add span events for key lifecycle moments — No span events were observed in the trace data. Adding events for connection establishment, TLS handshake, retry attempts, or circuit-breaker state changes would give operators richer timeline data within a single trace without adding new spans.
Publish architectural trace modeling documentation — Documenting the intended trace topology (which span kinds appear at which layers, how middleware spans relate to entry-point spans) would help operators understand what to expect in their traces and write correct alert queries.
2 Multi-Signal Observability All three signals via OTLP to same Collector. 100% of log records carry traceId/spanId. Six shared OTel semconv attribute keys enable metric-to-trace pivots. ▶

What we observed

All three signals flow via OTLP gRPC to the same Collector endpoint. The correlation quality is excellent: 100% of the 24 access log records carry both traceId and spanId in the OTLP envelope, and all 20 unique trace IDs from logs were verified against actual span data. Six shared OTel semconv attribute keys (http.request.method, http.response.status_code, network.protocol.version, server.address, server.port, url.scheme) enable metric-to-trace pivots without manual bridging. A full metric→trace→log investigative workflow is possible today.

What's working well

  • 100% log-to-trace correlation: every access log record carries both traceId and spanId, and all log trace IDs match verified spans — enabling direct pivots from log entries to full distributed traces.
  • Six shared OTel semconv attribute keys across metrics and traces enable metric-to-trace correlation without manual bridging or project-specific knowledge.

Opportunities

Document the cross-signal investigative workflow — The metric→trace→log pivot path works technically, but there is no documentation guiding operators through it. A worked example (e.g., "spike in traefik_router_requests_total with code=500 → find matching trace → correlate access log") would significantly improve operator experience.
Rationalize the dual metrics pipeline — Running both OTLP push and Prometheus scrape simultaneously creates naming inconsistencies (OTel semconv names vs traefik_* names) without documented rationale. Providing guidance on when to use each path, or a roadmap toward OTLP-primary, would reduce operator confusion.
1 Audience & Signal Quality Strong SLO-relevant metrics. Span naming is operator-unfriendly (GET bare method). Critical log severity mismatch breaks OTel-native routing. ▶

What we observed

Traefik emits strong SLO-relevant metrics: request rate, latency histograms, byte throughput, open connections, and config reload health at entrypoint, router, and service granularity. However, span naming reduces trace usability: entry-point spans are named GET (bare HTTP method, no route template), collapsing all requests onto a single span name. The ReverseProxy span exposes an internal component name. A critical log severity bug was identified: all 24 access log records carry severityText: "info" in the OTel envelope while the embedded JSON body contains "level": "panic" — breaking any OTel-native log routing or alerting based on severity.

What's working well

  • Rich SLO-relevant metric coverage at three levels of granularity: traefik_entrypoint_*, traefik_router_*, and traefik_service_* — plus OTel semconv http.server.request.duration and http.client.request.duration histograms.
  • Access log records are well-structured with rich context: RouterName, ServiceName, KubernetesIngressName, Duration, and 100% trace correlation via TraceId/SpanId.

Opportunities

Add route template to span names — Changing entry-point span names from GET to GET /api/v1/{resource} (method + matched route template) would make traces immediately useful for operators without requiring Traefik architecture knowledge. This is the primary blocker for Level 2 on this dimension.
Fix log severity mapping — The mismatch between severityText: "info" in the OTel envelope and "level": "panic" in the JSON body silently breaks OTel-native log routing and alerting. Correctly mapping Traefik internal log levels to OTel SeverityNumber is a contained fix with significant production impact.
2 Stability & Change Management Comprehensive metrics reference docs; dedicated migration guide for every telemetry-breaking change. Official Grafana dashboards maintained. ▶

What we observed

Traefik maintains comprehensive telemetry documentation: full metric reference tables with types, labels, and descriptions; dedicated migration guide sections for every telemetry-breaking change across versions; and official Grafana dashboards (IDs 17346 and 17347). The migration guide documents changes from v3.0 (full tracing overhaul), v3.3 (config renames), v3.3.4 (metric unit change from ms to seconds), v3.5.0 (new traceVerbosity option), and v3.5.4 (metric rename). Schema URLs are present on all three signals. However, trace and log instrumentation scope versions show vunknown while metrics correctly shows v3.7.0.

What's working well

  • Comprehensive per-version migration guide: every telemetry-breaking change has a dedicated named section with explicit user-impact descriptions — operators know exactly what changed and how to adapt.
  • Official Grafana dashboards (IDs 17346 and 17347) are maintained and referenced in docs — demonstrating a commitment to stable metric names that the community can build on.

Opportunities

Fix instrumentation scope versions for traces and logs — Trace and log instrumentation scopes show vunknown while metrics correctly carries v3.7.0. Aligning all three scopes to the project version enables automated telemetry regression detection and makes scope-based version filtering reliable.
Introduce dual-emission deprecation windows for metric renames — Currently, metric renames (e.g., traefik_tls_certs_not_after_milliseconds → traefik_tls_certs_not_after_seconds) take effect immediately. Emitting both old and new names for one release cycle would give operators time to migrate dashboards and alerts without service disruption.
Key takeaways

● Strengths

  • OTLP-native tracing with correct end-to-end propagation — Traefik v3 removed all legacy tracing exporters and made OTLP the sole backend. W3C Trace Context is correctly extracted and injected, confirmed by a 40-span trace continuing an externally-initiated trace ID across 5 parallel backend calls.
  • Excellent multi-signal correlation — 100% of access log records carry both traceId and spanId. Six shared OTel semconv attribute keys enable metric-to-trace pivots without manual bridging.
  • Proactive change management — Comprehensive per-version migration guide with named sections for every telemetry-breaking change, plus official Grafana dashboards demonstrating commitment to stable metric names.

● Priority improvements

  • Add route template to span names — Change entry-point span names from bare GET to GET /{route} to make traces immediately useful without Traefik architecture knowledge.
  • Fix log severity mapping — Correct the mismatch between severityText "info" in the OTel envelope and "level": "panic" in the JSON body — a contained fix with significant production impact on log routing and alerting.
  • Align metric attribute keys with OTel semconv — Replace abbreviated Prometheus labels (method, code, protocol) with OTel semconv keys (http.request.method, http.response.status_code, url.scheme) to enable cross-signal correlation.
  • Support standard OTEL_* env vars — Adopting OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_SERVICE_NAME as primary configuration surfaces would simplify deployment in OTel-aware environments and align with ecosystem standards.

● Notable observations

  • OTLP logs are experimental but functional — The --experimental.otlpLogs=true feature gate works reliably in practice. As it graduates to stable, Traefik's three-signal story will strengthen significantly.
  • service.instance.id absent from OTLP signals — In multi-replica deployments, distinguishing telemetry from individual Traefik pods requires relying on pipeline-enriched k8s.pod.name rather than a native service.instance.id.
  • Prometheus is the Helm default for metrics — New Helm deployments use Prometheus scrape by default; OTLP metrics push requires explicit opt-in. The path to OTLP-only is documented but requires deliberate action.
