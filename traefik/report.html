Dimension details
1 Integration Surface All three signals flow via native OTLP gRPC, but OTEL_EXPORTER_OTLP_ENDPOINT is unsupported, Prometheus remains the metrics default, and log OTLP is experimental ▶

What we observed

Traefik v3 natively pushes all three signals — traces, metrics, and logs — via OTLP gRPC using the OTel Go SDK v1.43.0 directly (telemetry.sdk.name: opentelemetry, telemetry.sdk.version: 1.43.0). Tracing is OTLP-exclusive: legacy exporters (Jaeger, Zipkin, Datadog tracing) were fully removed at v3.0. However, the signals are at three different maturity levels: tracing is OTLP-only (mature), metrics treats OTLP as one of five co-equal backends with Prometheus as the Helm chart default, and log OTLP requires the experimental.otlpLogs: true feature gate. The standard OTEL_EXPORTER_OTLP_ENDPOINT environment variable is not supported — users must configure three separate project-specific endpoint flags per signal.

What's working well

  • Tracing is fully OTLP-native with no legacy exporters — a strong commitment to the OTel ecosystem demonstrated by removing Jaeger, Zipkin, and Datadog tracing adapters entirely at v3.0
  • Standard OTel env vars OTEL_RESOURCE_ATTRIBUTES and OTEL_PROPAGATORS are respected via resource.WithFromEnv() and autoprop, and W3C Trace Context propagation is confirmed working end-to-end

Opportunities

Add OTEL_EXPORTER_OTLP_ENDPOINT support — Implementing the standard OTEL_EXPORTER_OTLP_ENDPOINT env var would allow operators to configure Traefik using the same mechanism as every other OTel-instrumented service, eliminating the need for three separate project-specific endpoint flags
Promote OTLP as the primary metrics backend and graduate log OTLP to stable — Making OTLP the Helm chart default for metrics (rather than Prometheus) and removing the experimental.otlpLogs: true feature gate would bring all three signals to the same integration maturity level as tracing

Checklist

  • ✓ All three signals flow via native OTLP gRPC push
  • ✓ OTel Go SDK used directly; OTEL_RESOURCE_ATTRIBUTES and OTEL_PROPAGATORS respected
  • ✗ OTEL_EXPORTER_OTLP_ENDPOINT not supported; three separate signal-specific endpoint flags required
  • ✗ Log OTLP behind experimental feature gate; Prometheus remains Helm chart default for metrics
1 Semantic Conventions Trace spans and two OTel metrics use current semconv, but the majority of traefik_* metrics use Prometheus-style attribute names and log attributes are entirely proprietary PascalCase ▶

What we observed

Traefik's own instrumentation scope (github.com/traefik/traefik) correctly uses current OTel HTTP semantic conventions on spans: http.request.method, http.response.status_code, url.path, url.full, url.scheme, server.address, network.peer.address, network.protocol.version, client.address, user_agent.original, http.route. Two OTel-standard metrics (http.server.request.duration, http.client.request.duration) also fully conform. However, the majority of traefik_* metrics use Prometheus-style short attribute names (method, code, protocol, entrypoint, router, service), and log attributes are entirely proprietary PascalCase (RequestMethod, DownstreamStatus, ClientAddr, RouterName). The same HTTP concept is named four different ways across signals.

What's working well

  • Traefik span attributes fully use current OTel HTTP semconv — http.request.method, http.response.status_code, url.path, server.address, network.protocol.version — demonstrating clear intent to align with the specification
  • Schema URL https://opentelemetry.io/schemas/1.40.0 is present on all three signals, and the documentation explicitly references OTel semconv v1.23.1

Opportunities

Migrate traefik_* metric attributes to OTel semconv naming — Renaming method → http.request.method, code → http.response.status_code, protocol → network.protocol.version in traefik_* metrics would enable off-the-shelf OTel dashboards to work without signal-specific normalization
Migrate log attributes from PascalCase to OTel semantic conventions — Replacing RequestMethod → http.request.method, DownstreamStatus → http.response.status_code, ClientAddr → client.address, RouterName → a semconv-aligned routing attribute would unify the attribute landscape across all three signals and enable cross-signal queries without field remapping
2 Resource Attributes & Configuration 15 natively detected resource attributes (service.name, service.version, telemetry.sdk.*, host.name, os.*, process.*) emitted consistently across all three OTLP signal paths ▶

What we observed

Traefik v3.7.0 uses the OTel Go SDK with automatic resource detection, emitting 15 natively detected resource attributes consistently across all three OTLP signal paths: service.name (traefik), service.version (3.7.0), telemetry.sdk.name, telemetry.sdk.language, telemetry.sdk.version, host.name, os.type, os.description, process.pid, process.executable.name, process.executable.path, process.owner, process.runtime.name, process.runtime.version, process.runtime.description. All k8s.* attributes are injected by the OTel Collector k8sattributes processor and do not count as natively emitted. service.name and service.version are consistent across all four signal paths. The undocumented precedence between tracing.serviceName config and OTEL_SERVICE_NAME env var is a minor gap.

What's working well

  • 15 resource attributes natively emitted via OTel Go SDK automatic detection — service.name, service.version, telemetry.sdk.*, host.name, os.*, process.* — consistently present across traces, metrics, and logs
  • service.name (traefik) and service.version (3.7.0) are correct and consistent across all signal paths — no identity misplacement as span or metric attributes

Opportunities

Document the full natively-emitted resource attribute set — Adding a documentation page listing all 15 natively emitted resource attributes, their sources, and stability guarantees would help operators understand what to expect without inspecting live telemetry
Emit service.instance.id natively and clarify OTEL_SERVICE_NAME precedence — Natively emitting service.instance.id (currently only collector-generated from Prometheus scrape URLs) and documenting whether tracing.serviceName takes precedence over OTEL_SERVICE_NAME would complete the resource identity story
2 Trace Modeling & Context Propagation Clean 7–8 span traces per request with correct SERVER/CLIENT span kinds; W3C Trace Context extraction and propagation confirmed working under concurrent load ▶

What we observed

Every proxied request produces a clean, coherent 7–8 span trace: entry-point GET span (SERVER kind) → ReverseProxy span (CLIENT kind) → backend handler spans (INTERNAL kind for middleware pipeline). W3C Trace Context extraction and propagation is confirmed working — when a test client sends a traceparent header, Traefik's entry-point span correctly uses the external span ID as its parentSpanId. This was verified under concurrent load (5 simultaneous requests), with all 5 Traefik spans correctly referencing the same external parent. Error paths (404s) maintain full trace continuity with status.code=2 (ERROR) and http.response.status_code=404 correctly set on ReverseProxy spans. 204 spans across 35 traces were observed, with 20 multi-span traces and 15 single-span traces (health checks/metrics scrapes).

What's working well

  • Entry-point spans consistently use SERVER kind and outbound proxy calls consistently use CLIENT kind — correct semantic modeling of Traefik's role as a reverse proxy
  • Trace topology is stable across concurrent and parallel requests and error paths — external traceparent headers are correctly extracted and propagated, verified with 5 simultaneous requests all correctly referencing the same external parent

Opportunities

Add span events to enrich trace understanding — Adding span events for key lifecycle moments (e.g., middleware selection, TLS handshake, retry attempts) would give operators richer timeline context within a trace without adding new spans
Populate instrumentation scope version and document sampling trade-offs — The instrumentation scope currently reports vunknown instead of a proper semantic version — fixing this would enable tooling to detect instrumentation library upgrades. Adding documentation on recommended sampling strategies for high-traffic proxy deployments would also help operators make informed decisions
2 Multi-Signal Observability 100% of log records carry traceId/spanId; verified span-level linkage enables a complete metric → trace → log investigative path without manual bridging ▶

What we observed

All three signals are flowing natively via OTLP: 204 trace spans, 742 metric series, and 24 log records. Cross-signal correlation is strong — 100% of log records (24/24) carry both traceId and spanId as first-class OTLP fields. Verified span-level linkage was confirmed: log spanId=ec661b5455bf83d6 matches the GET entry-point span in trace 9e74d9394fa15869a9fa04001b2b0c13. Six shared attribute keys exist between OTel metrics and traces: http.request.method, http.response.status_code, network.protocol.version, server.address, server.port, url.scheme. The complete metric → trace → log investigative path works end-to-end. The main friction point is the dual metric pipeline: legacy traefik_* metrics use different attribute keys from OTel-semantic metrics and traces.

What's working well

  • 100% of log records carry traceId and spanId as first-class OTLP fields — verified span-level linkage confirmed, enabling direct pivot from logs to the exact trace span that generated them
  • Six shared attribute keys between OTel metrics and traces (http.request.method, http.response.status_code, network.protocol.version, server.address, server.port, url.scheme) enable metric-to-trace drill-down without field remapping

Opportunities

Document multi-signal investigative workflows — Each signal is currently documented in isolation. Adding a runbook showing how to start from an http.server.request.duration spike, filter by shared attributes to narrow traces, and pivot to correlated logs via traceId/spanId would help operators leverage the full multi-signal capability
Unify attribute naming across the dual metric pipeline — The traefik_* Prometheus metrics use entrypoint, router, service, code, method while OTel metrics use http.request.method, http.response.status_code. Aligning the legacy metric attributes with OTel semconv would make the full 742-series metric set joinable with traces without schema translation
1 Audience & Signal Quality Missing http.route on server spans, no router/service context in traces, and a production-hazard log severity mismatch (severityText: "info" vs body "level": "panic") block Level 2 ▶

What we observed

Traefik's metric quality is strong — traefik_router_requests_total, traefik_router_request_duration_seconds, traefik_service_request_duration_seconds, and traefik_entrypoint_requests_total provide a full three-tier RED dashboard directly from the box. However, trace quality has critical gaps: spans carry url.path but never http.route — operators cannot group traces by route template or identify which Traefik router/service handled a request from trace data alone. The ReverseProxy span name exposes an internal component name with no route or service context. A production-hazard severity bug was found: all 24 log records carry severityText: "info" while the embedded JSON body contains "level": "panic" — alert rules based on OTel log severity will silently miss these events. Log attributes use non-OTel PascalCase naming (RouterName, ClientAddr, DownstreamStatus) inconsistent with traces and metrics.

What's working well

  • Metrics are the strongest signal layer — traefik_router_requests_total, traefik_router_request_duration_seconds, traefik_service_request_duration_seconds, traefik_entrypoint_requests_total provide a complete three-tier RED dashboard (entrypoint → router → service) usable without customization
  • Structured JSON access logs (one per proxied request) are operationally appropriate in volume and carry correct trace correlation fields, providing useful per-request context alongside trace data

Opportunities

Add http.route and router/service context to server spans — Adding http.route to server spans (the route template, e.g. /api/users/{id}) and including the Traefik router name and service name as span attributes would allow operators to group traces by route and identify routing context without cross-referencing logs or metrics
Fix the log severity mismatch — a production alerting defect — All 24 log records carry severityText: "info" while the embedded JSON body contains "level": "panic". Correcting the OTel severityText field to reflect the actual severity in the log body is critical — alert rules that filter on OTel log severity will silently miss these events in production
1 Stability & Change Management Telemetry changes tagged in changelog and schema URLs present on all signals, but no breaking-change labels, no stable/experimental annotations, and instrumentation scope reports vunknown ▶

What we observed

Traefik demonstrates meaningful but informal telemetry change management. Schema URLs are present on all three signals (traces and logs at 1.40.0, metrics at 1.18.0 and 1.40.0). Telemetry changes are consistently tagged in the changelog with [otel], [metrics,otel], [tracing,otel] labels. A comprehensive metrics reference page documents all traefik_* metric names, types, and labels. However, there are no "BREAKING" labels on breaking telemetry changes, no stable/experimental annotations on any telemetry signal, and no enumeration of emitted span names or span attributes in documentation. The instrumentation scope reports vunknown rather than a proper semantic version. User-reported breakage issues (#11114 metric unit, #11230 span name, #10928 metric removal) indicate a reactive rather than proactive approach to telemetry stability.

What's working well

  • Telemetry changes are consistently tagged in the changelog with [otel], [metrics,otel], [tracing,otel] — making it easy to find telemetry-related changes across releases
  • Comprehensive metrics reference page documents all traefik_* metric names, types, and labels; schema URLs are present on all three signals

Opportunities

Add BREAKING labels and stable/experimental annotations to telemetry changes — Explicitly marking breaking telemetry changes (metric renames, removals, unit changes) as "BREAKING" in changelogs and adding stable/experimental labels to metrics and span attributes in documentation would allow operators to proactively plan for upgrades rather than discover breakage reactively
Populate instrumentation scope version and add span reference documentation — Fixing the instrumentation scope version from vunknown to a proper semantic version, and adding a documentation page enumerating all emitted span names and their attributes (similar to the existing metrics reference page), would complete the telemetry provenance story
Key takeaways

● Strengths

  • First-class OTLP across all three signals with strong trace-log correlation — Traefik v3 natively pushes traces, metrics, and logs via OTLP gRPC. Every log record carries traceId and spanId as first-class OTLP fields with verified span-level linkage — the full metric → trace → log investigative path works end-to-end without manual bridging
  • Rich, consistent resource identity via the OTel Go SDK — 15 natively detected resource attributes (service.name, service.version, telemetry.sdk.*, host.name, os.*, process.*) emitted consistently across all signal paths with no identity misplacement
  • Correct and robust W3C Trace Context propagation with clean trace topology — Every proxied request produces coherent 7–8 span traces with correct SERVER/CLIENT span kinds; external traceparent headers correctly extracted and propagated under concurrent load; error paths maintain full trace continuity

● Priority improvements

  • Add http.route and router/service context to traces — Spans carry url.path but never http.route — the single highest-impact trace improvement; also add router name and service name as span attributes to enable routing context in traces
  • Fix the log severity mismatch — All log records carry severityText: "info" while the JSON body contains "level": "panic" — a production alerting defect that causes OTel-based alert rules to silently miss critical events
  • Support OTEL_EXPORTER_OTLP_ENDPOINT and promote OTLP as primary backend — Implementing OTEL_EXPORTER_OTLP_ENDPOINT, making OTLP the Helm chart default for metrics, and graduating log OTLP from experimental would allow standard OTel env var configuration and bring all signals to the same integration maturity as tracing
  • Migrate log and traefik_* metric attributes to OTel semconv naming — The same HTTP concept is named four different ways across signals — http.request.method (traces/OTel metrics), method (traefik_* metrics), RequestMethod (logs). Unifying to OTel semconv would enable cross-signal queries without field remapping

● Notable observations

  • Dual metric naming schemes create operational friction — Two coexisting metric families — http.server.request.duration with OTel semconv attributes, and traefik_* with Prometheus-style short names — require operators to understand both systems. The same concept (HTTP method) is named http.request.method in traces and OTel metrics, method in Traefik metrics, and RequestMethod in logs
  • Instrumentation scope version is unpopulated — The instrumentation scope reports vunknown (or ?) rather than a proper semantic version, preventing tooling from detecting instrumentation library upgrades and creating a gap in telemetry provenance
  • Log OTLP behind a feature gate limits production adoption — Requiring experimental.otlpLogs: true to enable log OTLP means most production deployments will not have logs flowing through the OTel pipeline, undermining the otherwise strong cross-signal correlation capability. The schema URL is present but decorative — deprecated attributes and proprietary naming persist despite the schema URL being set
