Dimension details
2 Integration Surface OTLP gRPC is the primary path for all three signals; Prometheus scrape remains as a parallel option ▶

What we observed

Traefik v3.7.1 supports OTLP gRPC natively for all three signals without adapters or sidecars. Traces are configured via --tracing.otlp.grpc.endpoint, metrics via --metrics.otlp.grpc.endpoint, and logs via --accesslog.otlp.grpc.endpoint and --log.otlp.grpc.endpoint. All three endpoints point to the same collector, and data was confirmed flowing on all three pipelines. Prometheus scraping remains available as a parallel compatibility option at /metrics. OTLP log export is behind the --experimental.otlpLogs=true feature gate.

What's working well

  • All three signals (traces, metrics, logs) are exported via OTLP gRPC natively — no adapters, sidecars, or custom glue code required to connect to a standard OTel Collector.
  • Prometheus scraping coexists as a backward-compatible option, making it easy for existing Prometheus-based stacks to migrate incrementally to OTLP.

Opportunities

Stabilize OTLP Log Export — Moving OTLP log export out of the --experimental.otlpLogs=true feature gate would signal production readiness. The feature appears stable based on observed telemetry data.
Support OTEL_* Environment Variables — Adding support for standard OTEL_EXPORTER_OTLP_ENDPOINT and related env vars alongside Traefik-specific flags would improve interoperability with OTel-native tooling and deployment patterns.

Checklist

  • ✓ OTLP gRPC supported natively for traces, metrics, and logs
  • ✓ All signals flow to the same collector endpoint without custom glue code
  • ✗ OTLP log export still behind experimental feature gate
  • ✗ Standard OTEL_* environment variables not supported; configuration uses Traefik-specific flags
1 Semantic Conventions Traces use current OTel HTTP semconv; traefik_* metrics use proprietary labels; log attributes use PascalCase proprietary names ▶

What we observed

Trace spans use current OTel HTTP semantic conventions with no deprecated attributes — http.request.method, http.response.status_code, url.path, url.query, url.scheme, server.address, network.protocol.version, client.address, and user_agent.original are all present. The schema URL https://opentelemetry.io/schemas/1.40.0 is set. However, the traefik_* metric family uses proprietary labels (code, method, protocol) instead of OTel semconv equivalents, and log attributes use PascalCase proprietary names like ClientAddr, DownstreamStatus, RequestMethod rather than OTel log conventions. severityText is null on all 13 application log records.

What's working well

  • Trace spans use current stable OTel HTTP semconv — no deprecated attributes like http.method or http.status_code were found. Schema URL is set correctly.
  • OTel semconv metrics http.server.request.duration and http.client.request.duration are emitted via OTLP with correct semconv attribute labels.

Opportunities

Align traefik_* Metric Labels with OTel Semconv — The traefik_entrypoint_requests_total, traefik_router_requests_total, and traefik_service_requests_total metrics currently use code, method, protocol. Migrating to http.response.status_code, http.request.method, network.protocol.name (with a deprecation period) would enable consistent tooling across both metric families.
Fix severityText and Adopt OTel Log Attribute Conventions — All 13 application log records have severityText: null despite severityNumber being set (9=INFO, 13=WARN). Populating severityText from the log level and mapping access log attributes (ClientAddr, RequestMethod) to OTel conventions (client.address, http.request.method) would improve log routing and correlation.
2 Resource Attributes & Configuration Rich native resource identity (service.name, service.version, telemetry.sdk.*, process.*, os.*); no service.instance.id on traces/OTLP metrics ▶

What we observed

Traefik emits a rich set of resource attributes natively via the OTel Go SDK: service.name: traefik, service.version: 3.7.1, telemetry.sdk.name: opentelemetry, telemetry.sdk.language: go, telemetry.sdk.version: 1.43.0, process.pid: 1, process.executable.name: traefik, process.executable.path: /usr/local/bin/traefik, process.owner: traefik, process.runtime.name: go, os.type: linux, and os.description. These are consistent across traces, OTLP metrics, and logs. The notable gap is service.instance.id, which is absent from traces and OTLP metrics — in Prometheus-scraped metrics, the collector sets it to a scrape-target-derived value, not from Traefik itself. Configuration uses Traefik-specific flags rather than standard OTEL_* env vars.

What's working well

  • service.name, service.version, and telemetry.sdk.* attributes are stable and consistent across all three signals — no collector enrichment needed for core identity.
  • Rich process and OS attributes (process.pid, process.executable.path, process.runtime.version, os.type, os.description) are emitted natively, giving operators deep runtime context without any additional configuration.

Opportunities

Add service.instance.id to Traces and OTLP Metrics — In multi-replica deployments, service.instance.id is needed to distinguish traces from different Traefik instances. Setting it to the pod UID or hostname (already available as host.name) would enable per-instance filtering without relying on collector enrichment.
Consistent Instrumentation Scope Versioning — The trace scope is github.com/traefik/traefik vunknown and the log scope is traefik vunknown — the version field is unpopulated. Only the metrics scope correctly shows v3.7.1. Consistent scope versioning across all signals would improve tooling compatibility.
1 Trace Modeling & Context Propagation All spans are flat SERVER spans with no child spans; W3C traceparent propagation confirmed; span name is bare HTTP method without route ▶

What we observed

All 235 observed spans are kind SERVER (kind=2) with no child spans. Each span is named GET — the bare HTTP method — with no route component. W3C Trace Context propagation is confirmed: Traefik reads incoming traceparent headers, creates a SERVER span with the incoming trace ID, and injects an updated traceparent into the upstream request. However, Traefik does not create a CLIENT span for the backend call. The entry_point attribute (values: traefik, web, metrics) identifies which entrypoint handled the request. The http.route attribute is absent from all spans despite Traefik having full routing context.

What's working well

  • W3C Trace Context (traceparent) propagation is confirmed working end-to-end — backends receive the correct trace context and can continue the same trace.
  • Entry-point spans are consistently SERVER kind with correct HTTP semconv attributes, providing a clean ingress-level view of every request handled by Traefik.

Opportunities

Add http.route and Improve Span Names — Traefik has full routing context (router name, matched route pattern). Adding http.route to spans and updating span names to GET /api/{id} format would enable route-level aggregation and make spans distinguishable without inspecting url.path.
Add CLIENT Spans for Backend Calls — Currently Traefik creates a SERVER span for the incoming request but no CLIENT span for the upstream call. Adding a CLIENT child span for each backend call would expose Traefik→backend latency in traces and complete the proxy hop picture.
1 Multi-Signal Observability All three signals flow via OTLP; access log trace correlation present but application logs lack severityText; signals not yet a correlated system ▶

What we observed

All three signals are present via OTLP gRPC. Access log records include traceId and spanId in the OTLP log record fields, enabling trace-log correlation for access logs. However, application logs (13 records: startup messages, provider events) have no traceId or spanId. The http.server.request.duration metric shares attribute keys with trace spans (http.request.method, http.response.status_code, server.address), but the traefik_* metrics use different labels (code, method) that don't align. Access logs also have duplicate trace ID fields: both TraceId/SpanId (PascalCase) and trace_id/span_id (snake_case) appear as separate log attributes.

What's working well

  • All three signals (traces, metrics, logs) flow via OTLP to the same collector endpoint — a strong foundation for building a correlated observability stack.
  • Access log records include traceId and spanId, enabling correlation between access logs and traces in backends like Grafana Tempo.

Opportunities

Add Trace Context to Application Logs — Application logs (startup messages, provider events, configuration changes) currently have no traceId or spanId. Injecting trace context where a request span is active would enable log-trace correlation beyond just access logs.
Deduplicate Trace ID Fields in Access Logs — Access log records currently include TraceId/SpanId (PascalCase), trace_id/span_id (snake_case), and the same values in the JSON body — triplication that suggests serialization through multiple code paths. Consolidating to the standard OTLP log record fields would reduce noise.
1 Audience & Signal Quality Span names are bare HTTP method; access log body is a JSON string; severityText missing from application logs; entry_point adds useful context ▶

What we observed

All 235 spans are named GET — the bare HTTP method. With addInternals: true, 224 of 225 observed spans came from internal traffic (Prometheus scraping, health checks, dashboard) and only 1 from actual user traffic. The entry_point attribute (values: traefik, web, metrics) adds useful filtering context. Application log records have severityNumber set (9=INFO, 13=WARN) but severityText is null for all 13 records. Access log body is a raw JSON string — operators must parse it to extract structured fields even though those same fields appear as log attributes. OTel semconv metrics (http.server.request.duration) are clean and usable, while traefik_* metrics require domain knowledge to interpret.

What's working well

  • The entry_point attribute provides useful operational context for filtering spans by entrypoint (web, traefik, metrics) — a Traefik-specific concept that helps operators navigate the trace data.
  • OTel semconv metrics (http.server.request.duration, http.client.request.duration) are clean, well-labeled histograms that work out-of-the-box with OTel-native dashboards.

Opportunities

Consider addInternals Default and Sampling Guidance — With addInternals: true, internal traffic (Prometheus scraping, health checks) dominates trace volume — 224/225 spans in the evaluation were internal. Documentation guidance on filtering by entry_point or adjusting addInternals would help operators get signal from the noise.
Structured Access Log Body — The access log body is currently a raw JSON string (the full access log line). Using a structured OTel log body (key-value map) instead of a serialized JSON string would eliminate the need for body parsing and reduce attribute duplication between the body and log attributes.
1 Stability & Change Management Telemetry changes mentioned in changelogs informally; OTLP log export still experimental; no explicit stability guarantees or migration guides ▶

What we observed

Traefik's changelog tags telemetry-related changes with categorical labels ([metrics,otel], [tracing], [logs,accesslogs]). Notable examples include a breaking metric unit change (milliseconds → seconds, #11523), a semconv upgrade to v1.26.0 (#10850), and the addition of OTLP log export. The schema URL https://opentelemetry.io/schemas/1.40.0 is set on trace and log exports. However, there are no explicit stability tiers for telemetry attributes or metric names, no migration guides for telemetry-specific changes, and the instrumentation scope version is vunknown for traces and logs. The breaking metric unit change was communicated in the changelog but without a deprecation period.

What's working well

  • Telemetry changes are tagged in the changelog with categorical labels ([metrics,otel], [tracing]), making it easier for operators to scan for relevant changes when upgrading.
  • Schema URL https://opentelemetry.io/schemas/1.40.0 is set on trace and log exports, showing awareness of OTel schema versioning.

Opportunities

Document Telemetry Stability Tiers — Adding explicit stability labels to metric names, span attribute names, and log attribute names in the documentation (e.g., "stable", "experimental") would help operators make informed decisions about which telemetry to build alerting and dashboards on.
Provide Migration Guides for Breaking Telemetry Changes — Breaking changes like the metric unit change from milliseconds to seconds (PR #11523) were communicated in the changelog without a deprecation period. A dedicated telemetry migration section in upgrade guides would reduce operator surprise when dashboards break after upgrades.
Key takeaways

● Strengths

  • Full OTLP Coverage — Traefik v3.7 is one of the few CNCF projects that supports OTLP push for traces, metrics, and logs natively, without sidecars or adapters. The integration works with a standard OTel Collector out of the box.
  • Rich Native Resource Identity — service.name, service.version, telemetry.sdk.*, process.*, and os.* are all emitted natively and consistently across all three signals. Operators get meaningful service identity without any collector enrichment.
  • Current OTel HTTP Semconv in Traces — Trace spans use current stable attributes — no deprecated http.method or http.status_code found. Schema URL https://opentelemetry.io/schemas/1.40.0 is set. W3C Trace Context propagation is confirmed working end-to-end.

● Priority improvements

  • Add http.route to Spans — Traefik has full routing context. Adding http.route and updating span names to GET /path/{param} format would enable route-level aggregation and make spans distinguishable in trace UIs.
  • Align traefik_* Metric Labels — Migrating traefik_entrypoint_requests_total and related metrics from code/method/protocol to OTel semconv labels would enable consistent dashboards and alerting across both metric families.
  • Fix severityText in Application Logs — All 13 application log records have severityText: null despite severityNumber being set correctly. This is likely a bug in the OTLP log exporter — a quick fix that would improve log routing in backends relying on severity text.
  • Add service.instance.id to Traces — In multi-replica deployments, service.instance.id is needed to distinguish traces from different Traefik pods. Setting it to the pod name or UID (already in host.name) would enable per-instance trace filtering natively.

● Notable observations

  • addInternals Inverts Traffic Ratio — With addInternals: true, 224 of 225 spans came from internal traffic (Prometheus scraping at entry_point=metrics, dashboard at entry_point=traefik) and only 1 from user traffic (entry_point=web). Operators should filter by entry_point=web to focus on user-facing traffic.
  • Dual Metric Families Require Operator Awareness — OTLP push includes http.server.request.duration (semconv-aligned) while Prometheus scrape does not. traefik_service_* metrics appear in both. Operators using only Prometheus scraping miss the semconv-aligned metrics — documentation should clarify which metric families are available on each transport.
  • Triplicated Trace IDs in Access Logs — Access log records include the trace ID three times: in the OTLP log record fields, as TraceId/SpanId (PascalCase) log attributes, and as trace_id/span_id (snake_case) log attributes — plus the same values embedded in the JSON body string. This triplication suggests the OTLP access log exporter serializes the same data through multiple code paths.
