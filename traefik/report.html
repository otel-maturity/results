Dimension details
1 Integration Surface OTLP supported for all signals but requires explicit per-signal opt-in; no OTEL_* endpoint env vars; Prometheus co-equal default ▶

What we observed

Traefik v3.7.0 supports OTLP gRPC export for all three signals natively using the OTel Go SDK (opentelemetry-go v1.43.0), confirmed by telemetry.sdk.name: opentelemetry on all signals. In our evaluation, all three signals flowed directly to an OTel Collector on port 4317 with zero sidecars or adapters. However, each signal requires its own separate Traefik-specific endpoint configuration block: --tracing.otlp.grpc.endpoint, --metrics.otlp.grpc.endpoint, and --accesslog.otlp.grpc.endpoint. The standard OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_EXPORTER_OTLP_PROTOCOL, and OTEL_SERVICE_NAME env vars are not honored for endpoint configuration. Prometheus metrics are enabled by default in the Helm chart while OTLP metrics must be explicitly added. OTLP log export requires the additional --experimental.otlpLogs=true feature gate.

What's working well

  • All three signals flow natively to an OTel Collector via OTLP gRPC — no wrappers, bridges, or sidecars needed. The OTel Go SDK is embedded in Traefik itself, producing rich telemetry with correct SDK metadata.
  • W3C Trace Context propagation is fully implemented and empirically verified: incoming traceparent headers are honored, trace IDs are preserved, and backend spans appear as children of Traefik's spans — zero context loss across 50 backend spans.

Opportunities

Support OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_EXPORTER_OTLP_PROTOCOL — Currently operators must configure three separate Traefik-specific endpoint blocks. Honoring the standard OTel SDK env vars would reduce configuration friction and align with how operators configure every other OTel-instrumented service in their fleet. This is the most impactful single change for operator experience.
Make OTLP the primary metrics path and clarify the Prometheus migration story — Prometheus metrics are enabled by default in the Helm chart while OTLP metrics must be explicitly added. Adding documentation guidance on when to prefer OTLP push over Prometheus scrape — and a roadmap for making OTLP the primary path — would reduce ambiguity and help operators avoid running duplicate metric pipelines simultaneously.

Checklist

  • ✓ OTLP export supported for all three signals via native OTel Go SDK (opentelemetry-go v1.43.0)
  • ✓ Connects directly to OTel Collector without adapters or sidecars
  • ✓ W3C Trace Context propagation fully functional and empirically verified
  • ✗ OTEL_EXPORTER_OTLP_ENDPOINT / OTEL_EXPORTER_OTLP_PROTOCOL env vars not honored for endpoint config
  • ✗ Prometheus scrape remains co-equal default; OTLP not clearly the recommended primary path
  • ✗ OTLP log export requires experimental.otlpLogs: true — not yet a stable default
  • ✗ Per-signal configuration fragmentation — no unified OTLP endpoint setting across traces, metrics, and logs
1 Semantic Conventions Trace spans fully current with zero deprecated attributes; traefik_* metrics use Prometheus shorthand labels; access log attributes are proprietary PascalCase ▶

What we observed

Traefik v3.7.0 trace spans use exclusively current OTel HTTP semantic conventions: http.request.method, http.response.status_code, url.path, url.full, url.scheme, server.address, client.address, network.protocol.version, and user_agent.original — all present with zero deprecated fields (http.method, net.host.*, net.peer.* are absent). OTLP-pushed metrics include http.server.request.duration and http.client.request.duration with correct OTel semconv attribute keys. However, the 15 traefik_* proprietary metrics use Prometheus-style shorthand attribute names (code, method, protocol) instead of OTel semconv equivalents. Access log attributes use Traefik-native PascalCase names (RequestMethod, DownstreamStatus, ClientHost) with no alignment to OTel semantic conventions. Schema URL https://opentelemetry.io/schemas/1.40.0 is present on all three OTLP signals.

What's working well

  • All Traefik trace spans use exclusively current stable OTel HTTP semconv — zero deprecated attributes observed. Span kinds are semantically correct: SERVER for entry-point spans, CLIENT for ReverseProxy upstream calls. Exception span events (exception.message, exception.stacktrace, exception.type) follow OTel conventions correctly.
  • Schema URL https://opentelemetry.io/schemas/1.40.0 is declared on all three OTLP signals, enabling schema-aware tooling to interpret the telemetry correctly. The OTLP-pushed http.server.request.duration and http.client.request.duration metrics are directly compatible with OTel-based dashboards.

Opportunities

Align traefik_* metric attribute names with OTel semconv — The traefik_entrypoint_requests_total and related metrics use code, method, and protocol labels. Updating these to http.response.status_code, http.request.method, and network.protocol.name would make the Prometheus metrics consistent with trace span attributes — enabling natural pivot between signals without custom label mapping in dashboards.
Map access log attributes to OTel semconv equivalents — Access log attributes currently use Traefik-native PascalCase names (RequestMethod, DownstreamStatus, ClientHost). Adopting OTel semconv names (http.request.method, http.response.status_code, client.address) would make logs interpretable by generic OTel tooling. The custom attribute entry_point should also be namespaced as traefik.entry_point.
3 Resource Attributes & Configuration Exemplary resource design: consistent identity across all signals, OTEL_RESOURCE_ATTRIBUTES with highest precedence, native K8sAttributesDetector ▶

What we observed

Traefik v3.7.0 sets an exceptionally rich and consistent set of resource attributes natively via the OTel Go SDK across all three signals: service.name=traefik, service.version=3.7.0, telemetry.sdk.name=opentelemetry, telemetry.sdk.language=go, telemetry.sdk.version=1.43.0, plus process attributes (process.pid, process.executable.name, process.executable.path, process.owner, process.runtime.name, process.runtime.version), OS attributes (os.type=linux, os.description), and Kubernetes attributes (k8s.pod.name, k8s.pod.uid, k8s.namespace.name) via Traefik's own K8sAttributesDetector (in pkg/types/k8sdetector.go). resource.WithFromEnv() is placed last in the resource chain across all three signal providers, giving OTEL_RESOURCE_ATTRIBUTES and OTEL_SERVICE_NAME the highest precedence — explicitly documented in the official Traefik docs.

What's working well

  • service.name=traefik and service.version=3.7.0 are perfectly consistent across traces, OTLP metrics, and logs — no identity misplacement, no attribute-level duplication. Traefik's native K8sAttributesDetector emits k8s.pod.name, k8s.pod.uid, and k8s.namespace.name without requiring any collector-side enrichment — a standout architectural advantage.
  • OTEL_RESOURCE_ATTRIBUTES is explicitly documented in the official Traefik reference docs and resource.WithFromEnv() is placed last in the resource chain across all three signal providers, giving env vars the highest override precedence — a best-practice implementation confirmed in source code.

Opportunities

Explicitly document OTEL_SERVICE_NAME support and add a precedence table — While OTEL_RESOURCE_ATTRIBUTES is documented, OTEL_SERVICE_NAME is not explicitly called out. Adding a clear precedence table (env vars override config, config overrides defaults) would help operators understand the full override model and reduce support questions.
Add service.instance.id natively using the pod UID — The pod UID is already available as k8s.pod.uid. Mapping it to service.instance.id would provide the standard OTel instance identity attribute that backends use for per-replica filtering, alerting, and cardinality management — a natural extension of the existing K8s resource detection.
2 Trace Modeling & Context Propagation W3C Trace Context verified end-to-end; correct SERVER/CLIENT span kinds; GET spans lack route templates; ReverseProxy is an internal component name ▶

What we observed

Traefik v3.7.0 produces a clean two-level trace structure: a SERVER span named GET for the inbound entry-point request, and a CLIENT span named ReverseProxy as a child for the outbound backend call. W3C Trace Context propagation is empirically verified — injecting traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 resulted in Traefik correctly preserving the trace ID, creating a child span, and propagating context to the backend. All 50 backend trace IDs are shared with Traefik trace IDs, confirming zero context loss across service boundaries. Error handling is semantically correct: 404 responses mark ReverseProxy CLIENT spans as status.code=ERROR while the parent GET SERVER span remains UNSET. The main limitation is that span names use only the HTTP method (GET) without a route template or http.route attribute, and ReverseProxy is an internal Go component name.

What's working well

  • W3C Trace Context (traceparent/tracestate) propagation is production-ready — empirically verified with zero context loss across 50 backend spans. A 40-span trace from injected context contains 5 complete request chains all correctly parented under the external span ID.
  • Span kinds are intentionally correct and semantically meaningful: SERVER (kind=2) for entry-point spans, CLIENT (kind=3) for upstream proxy calls. The --tracing.addInternals=true configuration option provides scope control for internal routes like /ping and /metrics.

Opportunities

Add http.route to SERVER spans using the matched router name — Traefik knows the matched router name at span creation time (available as RouterName in access logs). Exposing it as http.route would transform all-identical GET spans into route-aware spans like GET /api/v1/users/{id} — dramatically improving trace usability for "which route was slow" diagnostics, which is the core use case for an ingress controller.
Fix trace instrumentation scope version and rename ReverseProxy span — The github.com/traefik/traefik scope reports vunknown in traces (vs. v3.7.0 in metrics). Additionally, renaming ReverseProxy to something like HTTP upstream request would make the client span interpretable by operators without Traefik-specific knowledge.
2 Multi-Signal Observability All three signals via OTLP with full cross-signal correlation; exemplars in histograms; structured log body and experimental gate are the remaining gaps ▶

What we observed

All three signals are present and flowing via OTLP gRPC to the same collector endpoint. Cross-signal correlation is fully functional: exemplars in http.server.request.duration and http.client.request.duration histograms contain Trace ID + Span ID, enabling direct pivot from metric data points to specific traces. Every access log record has Trace ID and Span ID set at the OTLP protocol level, enabling direct correlation with traces. Resource attributes are perfectly consistent across all three signals — same service.name=traefik, service.version=3.7.0, k8s.*, and telemetry.sdk.* values. The three-layer metric hierarchy (entrypoint/router/service) covers the full RED pattern. OTLP log export remains behind experimental.otlpLogs: true, and log bodies are serialized as raw JSON strings rather than structured OTel log attributes.

What's working well

  • Exemplars in histogram metrics contain Trace ID + Span ID, enabling direct pivot from a latency spike in http.server.request.duration to the specific trace that caused it — without any collector-side enrichment or manual stitching.
  • Every access log record carries OTLP-level Trace ID and Span ID fields. Resource attributes are perfectly consistent across all three signals, enabling unified filtering by service.name, service.version, and Kubernetes identity in any OTel-aware backend.

Opportunities

Graduate OTLP log export from experimental to stable — Removing the experimental.otlpLogs: true gate would make all three signals available by default in OTel-native environments. The level: panic serialization bug in access log bodies is the natural prerequisite to fix before graduation — addressing it first would make the graduation straightforward.
Emit access log fields as structured OTel log attributes rather than a JSON string body — Currently the log body is a raw JSON string, with fields duplicated as OTLP attributes. Emitting the fields directly as structured log attributes would make the log body parseable by OTel-native consumers without a JSON parsing step, and would enable proper attribute-level filtering in log backends.
1 Audience & Signal Quality Strong three-layer metric hierarchy; ReverseProxy span name is internal Go component; level:panic log bug; url.full carries pod IPs ▶

What we observed

Traefik emits exactly two span types from its own scope: GET (SERVER, entry-point) and ReverseProxy (CLIENT, upstream call). The metric layer is genuinely strong — a well-structured three-layer hierarchy (entrypoint/router/service) covering the full RED pattern, plus OTel semantic convention metrics (http.server.request.duration, http.client.request.duration) with exemplars. However, several quality issues affect the trace and log signals: ReverseProxy is an internal Go struct name requiring Traefik-specific knowledge to interpret; url.full on ReverseProxy spans contains pod IPs (e.g., http://10.244.0.6:3000/) creating high cardinality in production with pod churn; ephemeral client.port and network.peer.port attributes add noise without diagnostic value; and all 44 access log records carry "level":"panic" in the JSON body regardless of HTTP status — a known Traefik v3 serialization bug that would trigger false severity alerts in production monitoring systems.

What's working well

  • The three-layer metric hierarchy (entrypoint → router → service) provides operationally useful RED metrics at every level of the Traefik routing stack. The OTLP http.server.request.duration and http.client.request.duration histograms with exemplars are directly compatible with OTel-based SLO tooling and dashboard templates.
  • Access log records provide rich per-request routing context — RouterName, ServiceName, KubernetesIngressName, RetryAttempts, Duration — that is operationally valuable for debugging routing issues even with non-standard attribute names. Trace ID and Span ID are correctly set at the OTLP protocol level on every record.

Opportunities

Fix the level:panic access log serialization bug — All access log records embed "level":"panic" in the JSON body regardless of HTTP status code. The OTLP severityText is correctly set to info, but the embedded body content would trigger false severity alerts in any monitoring system watching log body content. This is the highest-impact fix for production deployments using Traefik's log signal.
Rename ReverseProxy span, add http.route, and reduce high-cardinality attributes — Renaming ReverseProxy to something like HTTP upstream request, adding http.route from the matched router name, and replacing url.full (which contains pod IPs) with server.address+server.port would collectively transform the trace signal from Traefik-internal to operator-friendly with manageable cardinality.
2 Stability & Change Management Schema URLs on all signals; every breaking telemetry change has a migration guide; trace scope version is vunknown; no formal deprecation period ▶

What we observed

Traefik treats telemetry as part of its public contract. Schema URL https://opentelemetry.io/schemas/1.40.0 is present on all three OTLP signals. Every breaking telemetry change across v3.x minor versions has a dedicated entry in the official migration guide with old/new values and explicit migration instructions — examples include the traefik_tls_certs_not_after_milliseconds → traefik_tls_certs_not_after_seconds rename (v3.5.4), the request duration unit change ms → s (v3.3.4), and the tracing.globalAttributes → tracing.resourceAttributes config rename (v3.2→v3.3). The CHANGELOG uses consistent [metrics,otel], [tracing,otel], [logs,otel] tags. OTLP log export is explicitly gated behind experimental.otlpLogs: true. One gap: the trace instrumentation scope github.com/traefik/traefik reports version vunknown in traces while correctly reporting v3.7.0 in metrics.

What's working well

  • Every breaking telemetry change found across v3.x has a dedicated migration guide subsection with old/new values — the v3.5.4 metric rename, the v3.3.4 unit change, and the v3.2→v3.3 config key rename all have explicit migration instructions. Users are never surprised by silent breaking changes to their dashboards or alerts.
  • Schema URL https://opentelemetry.io/schemas/1.40.0 is correctly set on all three OTLP signals, and OTLP log export is explicitly marked experimental via the feature gate — demonstrating intentional, well-communicated stability signaling for new features.

Opportunities

Fix trace instrumentation scope version (vunknown → v3.7.0) — The github.com/traefik/traefik scope reports vunknown in traces while correctly reporting v3.7.0 in metrics. This inconsistency affects tooling that uses scope versions for filtering or routing, and is a small but meaningful gap in an otherwise strong stability story.
Introduce a formal deprecation period before breaking telemetry changes — The v3.3.4 duration unit change (ms → s) was immediately breaking with no deprecation period. Introducing a one-minor-version deprecation cycle — emitting both old and new metric names simultaneously before removing the old — would give operators time to update dashboards and alerts before the old name disappears.
Key takeaways

● Strengths

  • Exemplary resource attribute design (Dim 3: Level 3) — service.name and service.version are consistent across all three signals, OTEL_RESOURCE_ATTRIBUTES is documented and respected with highest precedence via resource.WithFromEnv() placed last in the chain, and Traefik's own K8sAttributesDetector natively emits k8s.pod.name, k8s.pod.uid, and k8s.namespace.name without any collector enrichment. This is the strongest dimension in the evaluation.
  • Telemetry treated as a public contract (Dim 7: Level 2) — Every breaking telemetry change across v3.x minor versions has a dedicated migration guide entry with old/new values. The CHANGELOG uses consistent [metrics,otel]/[tracing,otel]/[logs,otel] tags. Users are not surprised by silent metric renames or span behavior changes.
  • Complete multi-signal coverage with full cross-signal correlation (Dim 5: Level 2) — All three signals flow via OTLP. Exemplars in histogram metrics link to specific traces. Every log record carries OTLP-level Trace ID and Span ID. The three-layer metric hierarchy (entrypoint/router/service) directly supports SLO alerting.

● Priority improvements

  • Support OTEL_EXPORTER_OTLP_ENDPOINT (Dim 1) — The most significant gap for operators familiar with the OTel SDK model. Three separate Traefik-specific endpoint blocks instead of one unified env var is the biggest configuration friction point and the clearest path to Level 2 on Integration Surface.
  • Align traefik_* metric labels with OTel semconv (Dim 2) — HTTP method is http.request.method in traces, method in traefik_* metrics, and RequestMethod in logs. Three names for the same concept prevents generic OTel tooling from correlating across signals without custom mapping.
  • Fix level:panic access log serialization bug (Dim 6) — All access log records show "level":"panic" in the JSON body regardless of HTTP status. This would trigger false severity alerts in production monitoring systems and is a prerequisite for graduating OTLP log export from experimental.
  • Rename ReverseProxy span and add http.route (Dim 6) — ReverseProxy exposes an internal Go component name. Adding http.route from the matched router name would transform the trace signal from Traefik-internal to operator-friendly — the highest-impact trace quality improvement.

● Notable observations

  • Dual metrics paths are a double-edged sword — Both Prometheus scrape and OTLP push are active simultaneously. The OTLP push path provides OTel semconv metrics (http.server.request.duration) that the Prometheus path does not, but the traefik_* metrics on both paths use non-OTel attribute names. Operators must understand both paths to use the telemetry effectively, and the duplication creates risk of metric confusion.
  • Traefik is ahead of its overall score on resource attributes — The Level 3 score on Dimension 3 reflects genuinely excellent work that stands out among CNCF projects. The native K8sAttributesDetector, consistent identity across all signals, and documented OTEL_RESOURCE_ATTRIBUTES support with highest-precedence semantics are all production-grade behaviors worth highlighting as a model for other projects.
  • The experimental log gate is the right call — but fix the bug first — Marking OTLP log export as experimental (experimental.otlpLogs: true) is the correct stability signal. The level: panic serialization bug in access log records confirms the label is warranted. The natural path forward is: fix the bug → graduate to stable → enable by default in Helm chart.
