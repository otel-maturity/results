Dimension details
2 Integration Surface OTLP-only in v3 after clean removal of all legacy exporters; all 3 signals flow natively via OTLP gRPC ▶

What we observed

Traefik v3 completed a clean architectural break from v2 by removing all legacy tracing backends (Jaeger, Zipkin, Datadog) — OTLP is now the sole trace export path. All three signals (traces, metrics, access logs) flow natively via OTLP gRPC to the OTel Collector without any adapter or sidecar. Metrics run a dual pipeline: OTLP push (emitting OTel semconv metric names like http.server.request.duration) alongside a Prometheus scrape endpoint (emitting traefik_* series). OTLP log export requires the experimental.otlpLogs: true feature gate. Configuration uses Traefik-specific keys (tracing.otlp.grpc.endpoint) rather than the standard OTEL_EXPORTER_OTLP_ENDPOINT env var.

What's working well

  • Complete removal of legacy exporters in v3 makes OTLP the unambiguous first-class path — no competing options for traces
  • W3C Trace Context propagation confirmed end-to-end: incoming traceparent headers are read, trace IDs preserved, and updated headers forwarded to backends

Opportunities

Document OTEL_EXPORTER_OTLP_ENDPOINT support — Currently endpoint must be configured via Traefik-specific keys. Adding support for the standard OTEL_EXPORTER_OTLP_ENDPOINT env var would let users reuse their existing OTel configuration without Traefik-specific knowledge
Graduate OTLP log export from experimental — The experimental.otlpLogs: true gate prevents users from relying on log export in production. Stabilising this flag would complete the three-signal OTLP story and remove a friction point from the setup experience

Checklist

  • ✓ All three signals flow via OTLP gRPC without adapters or sidecars
  • ✓ Legacy exporters (Jaeger, Zipkin, Datadog) fully removed in v3 — no competing paths for traces
  • ✗ OTEL_EXPORTER_OTLP_ENDPOINT env var not documented as supported configuration path
  • ✗ OTLP log export gated behind experimental.otlpLogs: true feature flag — not yet stable
1 Semantic Conventions Traefik spans use current semconv; Prometheus metrics and log attributes use proprietary naming ▶

What we observed

Traefik's own 117 spans use current OTel semantic conventions correctly: http.request.method, http.response.status_code, url.path, url.scheme, network.peer.address, client.address, user_agent.original. OTel metrics (http.server.request.duration, http.client.request.duration) carry fully compliant attribute sets. However, the Prometheus-scraped traefik_* metrics use proprietary label names (code, method, protocol) instead of OTel names. Access log attributes use PascalCase proprietary naming (RequestMethod, DownstreamStatus, ClientAddr) with no OTel alignment, and log bodies are stringified JSON blobs rather than structured OTel attributes. Schema URL https://opentelemetry.io/schemas/1.40.0 is present on all three signals.

What's working well

  • Traefik's own trace spans consistently use current stable semconv attributes — http.request.method, http.response.status_code, url.path, network.protocol.version — with schema URL 1.40.0 declared
  • OTel semconv metrics http.server.request.duration and http.client.request.duration are emitted with fully compliant attribute sets including error.type

Opportunities

Align Prometheus metric label names with OTel semconv — traefik_* Prometheus metrics use code, method, protocol labels. Migrating to http.response.status_code, http.request.method, network.protocol.version would enable consistent cross-signal queries without label translation
Restructure access log attributes to use OTel semconv names — Log attributes currently use PascalCase proprietary names (RequestMethod, DownstreamStatus). Emitting structured OTel attributes with semconv names (http.request.method, http.response.status_code) and replacing the stringified JSON body with typed OTel log attributes would unlock consistent cross-signal correlation
3 Resource Attributes & Configuration Exemplary: full OTel SDK resource set plus native K8s identity detection via K8sAttributesDetector ▶

What we observed

Traefik achieves the highest possible level here. The OTel Go SDK populates a comprehensive resource attribute set natively across all three signals: service.name: traefik, service.version: 3.7.1, telemetry.sdk.name, telemetry.sdk.language, telemetry.sdk.version: 1.43.0, host.name, os.type: linux, os.description, and the full process.* group (process.pid, process.executable.name, process.executable.path, process.owner, process.runtime.name, process.runtime.version). Traefik also implements a custom K8sAttributesDetector that queries the Kubernetes API to natively populate k8s.pod.name, k8s.pod.uid, and k8s.namespace.name — without relying on Collector enrichment. All three signal providers use resource.WithFromEnv() as the final step, giving OTEL_SERVICE_NAME and OTEL_RESOURCE_ATTRIBUTES the highest override precedence.

What's working well

  • Native K8sAttributesDetector populates k8s.pod.name, k8s.pod.uid, and k8s.namespace.name at the source — no Collector-side enrichment needed for core Kubernetes identity
  • service.name: traefik and service.version: 3.7.1 are perfectly consistent across all three signals; OTEL_RESOURCE_ATTRIBUTES override is documented and tested with highest precedence via resource.WithFromEnv()

Opportunities

Add service.instance.id natively — The only resource attribute currently seen as service.instance.id is a Collector artifact (the Prometheus scrape target address). Emitting a stable, unique service.instance.id natively (e.g. based on pod UID) would improve multi-instance correlation in dashboards
Expand native K8s attribute coverage — The built-in K8sAttributesDetector currently covers pod name, UID, and namespace. Extending it to also detect k8s.deployment.name, k8s.node.name, and k8s.container.name natively would reduce dependency on Collector-side k8sattributes processor enrichment
2 Trace Modeling & Context Propagation Textbook-correct SERVER/CLIENT/INTERNAL span kinds; W3C Trace Context propagated end-to-end across service boundaries ▶

What we observed

Trace modeling is textbook-correct. All 72 root spans use kind=SERVER. Traefik emits ReverseProxy spans as kind=CLIENT, and the backend Express middleware spans are kind=INTERNAL — matching OTel semantic conventions precisely. W3C Trace Context is propagated end-to-end: traces span three independent instrumentation scopes (github.com/traefik/traefik, @opentelemetry/instrumentation-http, @opentelemetry/instrumentation-express) within a single traceId. Error cases correctly set status.code=2 on the ReverseProxy CLIENT span (where the error is observed) while backend SERVER spans remain UNSET. The 53 single-span traces are all for internal health endpoints (/ping, /metrics) — correctly isolated, not fragmented.

What's working well

  • 100% of root spans use kind=SERVER; ReverseProxy correctly uses kind=CLIENT; error status correctly placed on the CLIENT span where the error is observed
  • End-to-end W3C Trace Context propagation confirmed across three independent instrumentation scopes in a single trace — Traefik correctly injects traceparent into forwarded requests

Opportunities

Add route-template context to span names — Span names are currently GET (generic HTTP method) and ReverseProxy (internal component name). Using route-template-based names like GET /api/{resource}/{id} would make traces immediately actionable without requiring Traefik domain knowledge
Enrich spans with span events — No span events are currently used. Adding events for key lifecycle moments (e.g. TLS handshake, middleware execution, retry attempts) would give operators richer diagnostic data within existing traces without adding new spans
2 Multi-Signal Observability All 3 signals flowing; 100% of access log records carry matching traceId/spanId; 6 shared OTel semconv attributes across traces and metrics ▶

What we observed

All three signals are flowing via OTLP gRPC. The standout finding is that 100% of access log records (24/24) carry traceId and spanId fields byte-for-byte identical to the corresponding trace spans — enabling zero-friction metric → trace → log pivots. Traces and OTLP metrics share six OTel semconv attribute keys: http.request.method, http.response.status_code, network.protocol.version, server.address, server.port, url.scheme. Application-level logs (startup, config reloads, routing decisions) remain behind the --experimental.otlpLogs flag, so only HTTP access logs flow as OTLP logs. The dual metrics pipeline (OTLP push + Prometheus scrape) creates overlapping series without a documented rationale.

What's working well

  • 100% of access log records carry OTLP-level traceId and spanId matching the corresponding trace spans — metric-to-trace-to-log correlation works out of the box
  • Six shared OTel semconv attribute keys across traces and OTLP metrics enable direct cross-signal pivots in any OTel-aware backend without label translation

Opportunities

Stabilise application-level log export — Only HTTP access logs currently flow as OTLP logs. Graduating --experimental.otlpLogs to stable and ensuring startup errors, configuration reloads, and routing decisions are also exported would complete the observability picture for operators troubleshooting non-request issues
Document the cross-signal investigative workflow — Each signal is documented independently. A published guide showing how to move from a traefik_router_requests_total spike → correlated trace → access log entry would help operators get full value from the already-excellent signal correlation that Traefik provides
1 Audience & Signal Quality Metrics are SLO-ready; trace span naming (GET, ReverseProxy) needs route context; log severity mapping bug ▶

What we observed

Metrics are the standout signal: the three-tier traefik_entrypoint_* / traefik_router_* / traefik_service_* hierarchy provides excellent RED method coverage, and official Grafana dashboards (IDs 17346 and 17347) signal operator-friendly design intent. However, trace span naming is limited to two names from Traefik's own scope: GET (generic HTTP method, no route template) and ReverseProxy (internal component name requiring domain knowledge). A critical log severity bug was found: all 24 access log records report severityText: info at the OTel level, while the embedded JSON body contains "level": "panic" — a Logrus serialization issue that would cause severity-based alerting to silently fail for every access log entry.

What's working well

  • Three-tier metric hierarchy (traefik_entrypoint_*, traefik_router_*, traefik_service_*) provides SLO-ready RED method coverage; official Grafana dashboards (IDs 17346, 17347) demonstrate operator-focused design
  • OTel semconv metrics http.server.request.duration and http.client.request.duration are emitted alongside Traefik-native metrics, enabling off-the-shelf OTel dashboards to work without custom metric configuration

Opportunities

Fix the log severity mapping bug — All access log records currently report severityText: info at the OTel level while the JSON body carries "level": "panic" (a Logrus level artifact). Fixing the severity mapping so OTel severityNumber and severityText correctly reflect the actual log level would make severity-based alerting reliable
Use route-template span names — Span names GET and ReverseProxy require Traefik domain knowledge to interpret. Adopting route-template-based naming (e.g. GET /api/{id}) following OTel HTTP semconv recommendations would make traces immediately useful for operators unfamiliar with Traefik internals
2 Stability & Change Management Schema URLs on all signals; CHANGELOG consistently tagged; breaking changes have dedicated migration guide sections ▶

What we observed

Schema URL https://opentelemetry.io/schemas/1.40.0 is present on all three signals (traces, OTLP metrics, logs). The CHANGELOG consistently uses [otel], [metrics], [tracing], [logs] prefixes to tag telemetry changes. Breaking metric changes receive dedicated migration guide sections — for example, the traefik_tls_certs_not_after_milliseconds → traefik_tls_certs_not_after_seconds rename in v3.5.4 was explicitly called out with a migration path. Official Grafana dashboards (IDs 17346 and 17347) signal that the metrics surface is treated as a user-facing contract. The metrics instrumentation scope carries version v3.7.1, but the traces scope carries no version (unknown). No formal stable/experimental labeling exists per-metric, and no dual-emission deprecation window is used for metric renames.

What's working well

  • Breaking telemetry changes receive dedicated migration guide sections with explicit before/after examples — the v2→v3 Observability migration guide is a model of proactive telemetry communication
  • Schema URLs on all three signals and CHANGELOG tagging with [otel]/[metrics]/[tracing] prefixes demonstrate that telemetry is treated as a versioned, user-facing contract

Opportunities

Add stable/experimental labeling to telemetry docs — Currently there is no per-metric or per-signal stable/experimental designation. Adding explicit stability labels to the metrics reference table would let users know which metrics are safe to build SLOs on and which may change
Add version to the traces instrumentation scope — The metrics scope correctly carries version v3.7.1, but the traces scope reports unknown. Aligning the traces scope version with the release version would make it easier to correlate traces with the exact Traefik version that produced them
Key takeaways

● Strengths

  • Genuine OTLP-native integration surface — All legacy exporters (Jaeger, Zipkin, Datadog) were fully removed in v3. OTLP is the sole trace export path — a meaningful architectural commitment, not just an added option
  • Exemplary resource attribute completeness — Level 3 for resource attributes: full OTel SDK resource set plus a custom K8sAttributesDetector that natively populates k8s.pod.name, k8s.pod.uid, and k8s.namespace.name without Collector enrichment
  • Strong telemetry change management — Breaking telemetry changes receive dedicated migration guide sections. The CHANGELOG uses [otel]/[metrics]/[tracing] tags consistently. Official Grafana dashboards signal that metrics are treated as a stable user-facing contract

● Priority improvements

  • Cross-signal semantic consistency — HTTP concepts are named three different ways: http.request.method in traces/OTel metrics, method in Prometheus metrics, RequestMethod in logs. Aligning all signals to OTel semconv names would enable consistent cross-signal queries
  • Fix log severity mapping bug — Every access log record reports severityText: info at the OTel level while the body contains "level": "panic". This Logrus serialization bug causes severity-based alerting to silently fail for all access log entries
  • Route-template span naming — Only two span names are used: GET (lacks route context) and ReverseProxy (internal component name). Route-template names like GET /api/{id} would make traces immediately actionable for operators
  • Graduate OTLP log export to stable — OTLP log export is gated behind experimental.otlpLogs: true. Stabilising this and extending it to cover application-level logs (startup, config, routing) would complete the three-signal OTLP story

● Notable observations

  • Dual metrics pipeline — Traefik emits traefik_* metrics via both OTLP push and Prometheus scrape simultaneously. OTLP push additionally emits OTel semconv metrics (http.server.request.duration). No deprecation timeline exists for the Prometheus path
  • Excellent distributed trace coherence — Despite span naming concerns, the trace structure is textbook-correct. 100% of root spans use kind=SERVER, W3C Trace Context propagates across three service boundaries, and error status is correctly placed on the CLIENT span
  • Log body redundancy — Access log records embed TraceId/SpanId in four different forms (body JSON + span attributes + OTLP-level fields), suggesting the log serialization path was not designed with OTLP's native correlation fields in mind
