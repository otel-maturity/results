Dimension details
0 Integration Surface Metrics via Prometheus scrape only; OTLP not supported; tracing broken in 3.12.2 ▶

What we observed

Emissary's sole telemetry integration is a Prometheus /metrics endpoint on port 8877 (the diagd admin service). There is no OTLP export capability in the project itself. A TracingService CRD exists supporting four drivers — lightstep, zipkin, datadog, and opentelemetry — but the opentelemetry driver is explicitly marked "work-in-progress, not for production use" in 3.12.2. All tracing drivers are non-functional due to an ADS cluster override bug that silently prevents span delivery. The LogService CRD uses Envoy's ALS gRPC protocol, which is incompatible with OTLP.

What's working well

  • The opentelemetry tracing driver exists in the TracingService CRD, demonstrating intent to support OTel natively — a foundation to build on once the ADS cluster override bug is resolved.
  • The Prometheus /metrics endpoint on port 8877 provides a rich, well-established metrics surface that any OTel Collector with a prometheus receiver can immediately consume — giving operators a working path to OTel pipelines today.

Opportunities

Fix the ADS tracing cluster override bug — The tracing cluster (otel_collector_opentelemetry_collector_opentelemetry_9411) receives 0 requests despite Envoy sampling 75 requests. Resolving the ADS server's override of the static tracing cluster would immediately unlock span delivery for all four drivers — including the OTel driver.
Add native OTLP metrics export — Integrating an OTel SDK into the diagd control plane (Python) would enable OTLP push for metrics, eliminating the need for users to deploy a Prometheus receiver in their collector pipeline and enabling native resource attributes like service.name and service.version.

Checklist

  • ✓ opentelemetry tracing driver present in TracingService CRD (intent demonstrated)
  • ✓ Prometheus /metrics endpoint is reachable and ingestible via OTel Collector prometheus receiver
  • ✗ OTLP export not supported natively — no SDK integration in diagd or Envoy data plane
  • ✗ Tracing is non-functional in 3.12.2; OTEL_* environment variables not respected
0 Semantic Conventions Proprietary envoy_* / ambassador_* naming; no OTel semantic conventions applied ▶

What we observed

All 407 metrics use Emissary/Envoy-proprietary naming derived from Envoy's internal stats subsystem — names like envoy_cluster_upstream_rq_total, envoy_http_downstream_cx_active, ambassador_reconfiguration_time_seconds, and envoy_http_tracing_random_sampling. Metric labels use Envoy-internal identifiers: envoy_cluster_name, envoy_http_conn_manager_prefix, envoy_response_code, envoy_worker_id. There is no alignment with OTel semantic conventions for HTTP metrics (http.server.request.duration), network metrics, or any other established OTel namespace. No schema URL is present on Emissary-native telemetry.

What's working well

  • Metric naming is internally consistent and follows Envoy's well-documented stats naming conventions, making them familiar to operators with Envoy experience and compatible with existing Envoy-specific dashboards.
  • The ambassador_* namespace (e.g., ambassador_reconfiguration_time_seconds, ambassador_diagnostics_errors) creates a clear, project-specific prefix that is easy to filter and identify in mixed-metric environments.

Opportunities

Map key metrics to OTel semantic convention names — High-value mappings to prioritize: envoy_http_downstream_rq_total → http.server.request.count, envoy_response_code label → http.response.status_code, envoy_http_downstream_cx_active → http.server.active_requests. Even an OTel Collector transform processor can bridge the gap while native renaming is planned.
Add a schema URL to Emissary-native telemetry — Adding https://opentelemetry.io/schemas/1.x.x as a schema URL to the instrumentation scope would enable consumers to understand the semantic convention version in use and perform automated schema migration when conventions evolve.
0 Resource Attributes & Configuration No native resource attributes; service.name and all k8s attributes are collector-derived; no OTEL_* support ▶

What we observed

Emissary emits zero native resource attributes. The project does not use an OTel SDK and does not set any resource attributes in its telemetry output. All identity on the metrics — service.name: emissary-ingress, k8s.pod.name, k8s.namespace.name: emissary, k8s.deployment.name, container.image.tag: 3.12.2 — is injected by the OTel Collector's k8sattributes processor and Prometheus receiver metadata. No OTEL_* environment variables are supported. service.version is absent from all signals even after collector enrichment.

What's working well

  • Emissary's Helm chart includes Prometheus scrape annotations on pods, enabling the OTel Collector's k8sattributes processor to reliably derive rich Kubernetes resource context (k8s.pod.name, k8s.namespace.name, k8s.replicaset.name, etc.) without any manual configuration.
  • The Prometheus target address (10.244.0.7:8877) is used as service.instance.id by the collector, providing a unique instance identifier per pod — useful for per-instance alerting even if not a stable OTel-native identity.

Opportunities

Emit service.name and service.version natively — Adding OTEL_SERVICE_NAME and OTEL_SERVICE_VERSION support to the diagd Python control plane (using the OTel Python SDK's resource detection) would make identity portable and independent of collector configuration. At minimum, the Helm chart could expose these as configurable environment variables.
Ensure consistent identity across all signals — Once tracing and logging are functional, using the same service.name, service.version, and service.instance.id across all three signals will enable seamless pivot between metrics, traces, and logs in observability backends — the key enabler for cross-signal correlation.
0 Trace Modeling & Context Propagation Emissary emits zero spans; tracing architecturally broken in 3.12.2; W3C traceparent passed through passively ▶

What we observed

Emissary emits zero spans. A TracingService CRD was applied with both Zipkin (port 9411) and OTel (gRPC/4317) drivers, but the tracing cluster (otel_collector_opentelemetry_collector_opentelemetry_9411) shows envoy_cluster_upstream_rq_total = 0 across all scrape intervals, despite Envoy correctly sampling 75 requests (envoy_http_tracing_random_sampling{envoy_http_conn_manager_prefix="ingress_https"} = 75). Emissary does pass through W3C traceparent headers to upstream services — evidence from backend traces shows parent span IDs, confirming passive header forwarding works.

What's working well

  • W3C traceparent header pass-through is working correctly — upstream services that receive requests through Emissary can participate in distributed traces initiated by clients, enabling end-to-end trace context without Emissary needing to generate its own spans.
  • The TracingService CRD architecture — with configurable sampling rates and multiple driver options — provides a solid CRD-based configuration model that, once the ADS bug is fixed, would allow operators to configure tracing without modifying Envoy bootstrap configs directly.

Opportunities

Resolve the ADS tracing cluster override to unlock span emission — Envoy is already sampling requests (envoy_http_tracing_random_sampling = 75) — the infrastructure is in place. Fixing the cluster override so the static tracing bootstrap cluster is not replaced by the ADS-pushed dynamic cluster would immediately enable span delivery without any other code changes.
Promote the OTel tracing driver from WIP to production-ready — Once span delivery is working, graduating the opentelemetry driver to stable would allow Emissary to generate Envoy-side HTTP spans with proper http.request.method, http.response.status_code, url.path, and server.address attributes — enabling Emissary to appear as a parent span in distributed traces.
0 Multi-Signal Observability Only metrics are first-class; traces and logs not flowing from Emissary; no cross-signal correlation ▶

What we observed

Only one signal (metrics) is first-class and functional. Traces are architecturally broken (0 spans delivered). Logs are not supported via OTLP — the LogService CRD uses Envoy's ALS gRPC protocol, which is incompatible with the OTel Collector's OTLP receiver. There is no cross-signal correlation: metrics have no trace context (trace_id, span_id), there are no logs to correlate, and no Emissary-generated parent span exists to link backend traces. Operators investigating an issue from metrics have no path to traces or logs from the same request.

What's working well

  • The metrics signal is comprehensive and operationally rich — 407 metrics covering request rates, error rates, circuit breaker states, connection counts, and control plane config compilation timings provide a solid foundation for a metrics-centric observability practice.
  • The CRD-based architecture (TracingService, LogService) shows the project's intent to support multi-signal observability at the configuration layer — the abstractions are in place, they just need the underlying implementations to be completed and stabilized.

Opportunities

Fix tracing to enable the second signal — Resolving the ADS cluster override bug would immediately add a second functional signal (traces), enabling operators to pivot from envoy_http_downstream_rq_total metrics spikes to the individual request spans that caused them — a transformative improvement in root cause analysis capability.
Add OTLP log export for access logs — Implementing an OTLP log exporter for Envoy's access logs (replacing or supplementing the ALS-based LogService CRD) would complete the three-signal picture. Access logs with trace_id correlation would allow operators to jump from a metric anomaly → trace span → structured access log entry for the same request.
1 Audience & Signal Quality 407 Prometheus metrics provide genuine operational value; Envoy-internal label naming requires domain expertise ▶

What we observed

Emissary exposes 407 unique Prometheus metrics covering the full Envoy proxy data plane and Ambassador control plane. Operationally valuable metrics include envoy_http_downstream_rq_total (request counts with per-listener breakdown), envoy_cluster_upstream_rq_total (per-cluster upstream counts), envoy_cluster_circuit_breakers_* (circuit breaker state), ambassador_reconfiguration_time_seconds (control plane config reload latency), and ambassador_diagnostics_errors (config error count). However, the metrics are not curated — all Envoy internal stats are exposed with no tiering between operational and debug metrics. Label values like envoy_cluster_name: otel_eval_backend_demo_3000 and envoy_http_conn_manager_prefix: ingress_https require Envoy-specific knowledge to interpret.

What's working well

  • The breadth of 407 metrics is genuinely impressive — operators familiar with Envoy have deep visibility into every subsystem: connection managers, cluster load balancing, circuit breakers, health checks, TLS handshakes, and control plane reconfiguration cycles.
  • The unique ambassador_* control plane metrics (e.g., ambassador_ir_time_seconds, ambassador_aconf_time_seconds, ambassador_fetcher_time_seconds) provide Emissary-specific operational value that is not available from raw Envoy — enabling diagnosis of CRD reconciliation and config compilation issues.

Opportunities

Introduce tiered metric documentation (operational vs. debug) — Publishing a curated list of "golden signal" metrics (e.g., envoy_http_downstream_rq_total, envoy_cluster_upstream_rq_time_*, ambassador_reconfiguration_time_seconds, ambassador_diagnostics_errors) would dramatically reduce the learning curve for operators unfamiliar with Envoy internals and enable off-the-shelf dashboard templates.
Provide OTel Collector transform processor recipes — Shipping example OTel Collector configurations with metricstransform or transform processor rules that rename envoy_response_code → http.response.status_code and remap key metrics to OTel semconv names would immediately improve signal quality for users without requiring any changes to Emissary itself.
0 Stability & Change Management No telemetry documentation as contract; no schema URL; tracing marked WIP; no change governance process ▶

What we observed

Emissary's telemetry is treated as an implementation detail rather than a user-facing contract. There is no telemetry reference page documenting metric names, labels, and their meanings. The TracingService CRD documentation lists supported drivers but does not clearly distinguish stable from experimental. The OpenTelemetry tracing driver is labeled "work-in-progress, not for production use" in runtime logs but this is not prominently documented. No schema URL is present on any Emissary-native telemetry. Metric names follow Envoy's internal stats naming, which can change silently when Emissary upgrades its Envoy dependency. Release notes do not contain dedicated sections for telemetry changes.

What's working well

  • The runtime warning ("work-in-progress, not for production use") for the OTel tracing driver demonstrates awareness of stability concerns — the project is being honest about what is and isn't ready, which is a positive signal even if the communication channel (runtime logs) is not ideal.
  • The CRD-based configuration model for TracingService and LogService provides a natural versioning boundary — CRD schema versions can be used to communicate breaking changes in telemetry configuration, a pattern already familiar to Kubernetes operators.

Opportunities

Publish a telemetry reference page as a stable contract — Documenting the curated set of operational metrics (names, labels, types, units, and stability status) as an official reference would let users build dashboards and alerts with confidence. Including a note like "metric names may change when the Envoy dependency is upgraded" sets correct expectations and prevents silent breakage.
Add a "Telemetry changes" section to release notes — Explicitly calling out metric additions, renames, or removals in each release's changelog (especially those caused by Envoy version bumps) would allow users to proactively update their dashboards and alert rules, treating telemetry changes with the same care as API changes.
Key takeaways

● Strengths

  • Comprehensive Prometheus metrics — 407 unique Envoy + Ambassador metrics covering request rates, error rates, circuit breakers, connection counts, and control plane config timing — genuinely useful for operators familiar with Envoy.
  • W3C Trace Context pass-through — Emissary correctly forwards traceparent headers to upstream services, enabling downstream services to participate in distributed traces initiated by clients — correct behavior for a transparent proxy.
  • Unique control plane metrics — ambassador_reconfiguration_time_seconds, ambassador_ir_time_seconds, and ambassador_diagnostics_errors expose Emissary-specific control plane internals that are valuable for diagnosing CRD reconciliation issues.

● Priority improvements

  • Fix the ADS tracing cluster override bug — Highest-priority fix — Envoy is already sampling requests but delivering 0 spans. Resolving this unlocks tracing for all four drivers immediately.
  • Adopt OTel SDK for OTLP-native metrics — Replace or supplement the Prometheus endpoint with OTLP push using the OTel Python SDK in diagd, enabling native service.name, service.version, and OTel semconv metric names.
  • Align metric naming with OTel semantic conventions — Map key metrics like envoy_http_downstream_rq_total → http.server.request.count and labels like envoy_response_code → http.response.status_code to enable off-the-shelf OTel dashboards and alerts.
  • Document telemetry as a stable contract — Publish a telemetry reference page with metric names, labels, stability status, and a changelog section for telemetry changes — treating observability as a first-class API surface.

● Notable observations

  • Tracing is fundamentally broken in 3.12.2 — silently — Envoy correctly samples 75 requests (envoy_http_tracing_random_sampling = 75) but delivers 0 spans. No error is logged, no metric indicates the problem. This is a silent failure that would cause operators to believe tracing is configured when it isn't.
  • service.name is entirely collector-derived — The value service.name: emissary-ingress in the telemetry is inferred by the OTel Collector from Prometheus scrape job annotations — not set by Emissary itself. Users who change their collector configuration could inadvertently change the service identity, breaking dashboards and alerts.
  • v4.x exists but is not yet Helm-installable — GitHub shows a v4.0.1 release that appears to be a major rewrite potentially with improved OTel support, but it is not yet available in the datawire Helm repository. This evaluation covers 3.12.2 — the latest Helm-installable stable version. The v4 trajectory may significantly change this assessment.
