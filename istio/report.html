Dimension Details
2 Integration Surface OTLP for traces & logs; Prometheus-only for metrics ▶

What we observed

Istio exports traces and access logs via OTLP gRPC directly to an OTel Collector using the meshConfig.extensionProviders configuration with the opentelemetry and envoyOtelAls extension types. Metrics are exposed only as Prometheus endpoints on ports 15014 (istiod), 15090 (Envoy sidecars), and 15020 (ingress gateway) — there is currently no native OTLP metrics export. Configuration is managed through Istio's own Telemetry CR (telemetry.istio.io/v1), not OTEL_* environment variables, which is appropriate for a mesh-level infrastructure component.

What's working well

  • Traces and logs connect directly to an existing OTel Collector on port 4317 — no adapters, bridges, or custom sidecars required.
  • OpenTelemetry is explicitly documented as the recommended tracing backend, preferred over legacy Zipkin/Jaeger providers.
  • The Telemetry CR provides a clean, Kubernetes-native, namespace-scoped configuration API that is more ergonomic than the older EnvoyFilter approach.
  • Sampling rate is configurable per-namespace via randomSamplingPercentage in the Telemetry CR.

Opportunities

Add native OTLP metrics export — The absence of OTLP metrics export forces a parallel Prometheus scraping pipeline alongside OTLP push for traces and logs. Adding an opt-in OTLP metrics exporter (even alongside Prometheus) would unify the integration model and unlock service.name-based correlation between metrics and traces.
Document the split integration model — Istio's documentation does not explicitly explain that traces/logs use OTLP push while metrics require Prometheus pull. A clear "telemetry architecture" page describing this split, and guidance for configuring both pipelines together, would reduce operator confusion.

Checklist

  • ✅ OTLP export supported for traces and logs
  • ✅ Users connect to an existing OTel Collector without adapters (just configure the service address)
  • ✅ OpenTelemetry documented as the recommended path for traces
  • ✅ Legacy Zipkin/Jaeger providers remain available but are not the default recommendation
  • ❌ Metrics require Prometheus scraping — no OTLP metrics export path
  • ❌ Configuration is not via OTEL_* env vars but via Istio's own meshConfig API
  • ❌ Telemetry configuration is inconsistent across signals (OTLP for traces/logs, Prometheus for metrics)
1 Semantic Conventions Deprecated HTTP attributes; proprietary Prometheus label schemas; unstructured log bodies ▶

What we observed

Envoy emits HTTP span attributes using the pre-1.21 OpenTelemetry conventions, all of which are now deprecated. Attributes such as http.method, http.status_code, http.url, http.protocol, net.host.ip, net.host.port, net.peer.ip, net.peer.port, and net.transport are present — but none of their current stable equivalents (http.request.method, http.response.status_code, url.full, server.address, server.port, network.peer.address) appear. Span kinds are correctly applied (SERVER/CLIENT). Prometheus metrics use Istio's proprietary label schema (source_workload, destination_workload, response_flags, etc.) with no alignment to OTel HTTP semconv. Access logs are unstructured text strings with no severity, no scope name, and no structured attributes.

What's working well

  • Span kinds are correctly set: gateway inbound spans are SPAN_KIND_SERVER, gateway outbound spans are SPAN_KIND_CLIENT, sidecar inbound spans are SPAN_KIND_SERVER — enabling tooling to interpret the trace topology correctly.
  • traceId and spanId are correctly set as proper OTLP fields on log records (not as string attributes), enabling native trace-log correlation in OTel-aware backends.
  • Envoy-proprietary attributes like istio.canonical_service, upstream_cluster, and response_flags provide useful mesh-specific context for Istio operators, even if they lack OTel equivalents.

Opportunities

Migrate Envoy HTTP attributes to current stable semconv — Updating from http.method → http.request.method, http.status_code → http.response.status_code, http.url → url.full, and net.host.*/net.peer.* to server.*/network.* equivalents would bring Istio to Level 2 on this dimension. This is an upstream Envoy dependency that Istio can advocate for or contribute.
Structure access log records — Currently, the ALS log body is a raw Envoy format string (e.g., [2026-05-07T16:06:35.689Z] "GET / HTTP/1.1" 200 - via_upstream...). Emitting structured log attributes (http.request.method, http.response.status_code, url.path, http.request.duration) and setting a meaningful SeverityNumber would transform access logs into a first-class structured signal.
Add schemaUrl to OTLP exports — No schemaUrl is currently set on Envoy's OTLP trace or log exports. Adding the appropriate schema URL (e.g., https://opentelemetry.io/schemas/1.26.0) would allow backends to correctly interpret and migrate attribute names.

Checklist

  • ✅ OTLP protocol used for traces and logs
  • ✅ Span kinds correctly applied (SERVER/CLIENT)
  • ✅ traceId/spanId set as proper OTLP fields on log records
  • ❌ All HTTP span attributes use deprecated conventions (http.method, http.status_code, http.url)
  • ❌ No current stable semconv attributes present (http.request.method, http.response.status_code, url.full)
  • ❌ Prometheus metric labels do not align with OTel HTTP semantic conventions
  • ❌ Log body is unstructured text, not structured OTel log semantic conventions
  • ❌ No schemaUrl on OTLP exports
  • ❌ Istio-proprietary span attributes (istio.mesh_id, upstream_cluster, response_flags) not documented as semantic extensions
1 Resource Attributes & Configuration Inconsistent service.name across signals; no service.version; metrics use scrape-job names ▶

What we observed

Envoy sets service.name natively in OTLP trace resource attributes, but the naming is inconsistent: gateway spans use istio-gateway.istio-system (workload + namespace suffix), backend sidecar spans use otel-eval-backend.demo (same pattern), but the backend app SDK spans use otel-eval-backend (no namespace suffix). This creates three different service.name values for two conceptual services. Metrics use scrape-job names (istio-envoy-sidecars, istio-ingressgateway), entirely disconnected from workload identity. Logs have no service.name at all. service.version and service.instance.id are absent across all signals.

What's working well

  • service.name is set natively by Envoy on trace resource attributes — no collector-side enrichment required for basic service identification in traces.
  • telemetry.sdk.name=envoy, telemetry.sdk.language=cpp, and telemetry.sdk.version correctly identify the instrumentation layer on trace resources.
  • After collector enrichment via k8sattributes, k8s.pod.name and k8s.namespace.name provide a workable cross-signal correlation key for traces and logs (though not metrics).

Opportunities

Unify service.name across signals — Adopting a consistent convention (e.g., the Kubernetes workload name without namespace suffix, with service.namespace as a separate attribute) and propagating it to metrics resources would enable metric-to-trace correlation. At minimum, documenting the recommended join key (e.g., k8s.pod.name) for cross-signal correlation would help operators build working dashboards.
Propagate service.version from canonical revision — Istio already tracks istio.canonical_revision on spans and source_canonical_revision/destination_canonical_revision on metrics. Mapping this to service.version as a resource attribute on OTLP exports would enable version-based traffic analysis in OTel-native tooling without any new data collection.
Set service.name on log resources — ALS log records currently have no service.name on the resource (only traceId/spanId as OTLP fields). Propagating the same service.name used in traces to log resources would enable service-level log filtering and correlation in backends.

Checklist

  • ✅ service.name is set on trace resource (by Envoy natively)
  • ✅ telemetry.sdk.name=envoy correctly identifies the instrumentation
  • ❌ service.name is inconsistent: namespace-appended for Envoy spans, not appended for app SDK spans
  • ❌ service.name is absent from log resource attributes
  • ❌ service.name in metrics uses scrape job names, not workload identity
  • ❌ service.version absent across all signals
  • ❌ service.instance.id absent from traces and logs
  • ❌ OTEL_SERVICE_NAME / OTEL_RESOURCE_ATTRIBUTES not respected (by design, but still a gap)
  • ❌ Identity cannot be correlated across traces, metrics, and logs by service.name
2 Trace Modeling & Context Propagation W3C Trace Context propagated correctly; coherent 4-layer span trees; Envoy-to-SDK context flow confirmed ▶

What we observed

A complete end-to-end trace for a single HTTP request through the Istio mesh produces a coherent 9-span tree. The trace spans three services and four instrumentation layers: (1) Istio Gateway Envoy inbound SERVER span (root), (2) Istio Gateway Envoy outbound CLIENT span (egress to backend), (3) Backend sidecar Envoy inbound SERVER span, and (4) Backend Node.js OTel SDK HTTP server span plus Express middleware spans. W3C Trace Context (traceparent/tracestate) is propagated correctly across all boundaries, including from Envoy into the application's inbound request headers where the OTel SDK picks it up as the parent context. 100% sampling is configurable via randomSamplingPercentage: 100 in the Telemetry CR.

[istio-gateway.istio-system] otel-eval-backend.demo.svc.cluster.local:3000/* (SERVER, ROOT)
  └─ [istio-gateway.istio-system] router outbound|...; egress (CLIENT)
       └─ [otel-eval-backend.demo] otel-eval-backend.demo.svc.cluster.local:3000/* (SERVER)
            └─ [otel-eval-backend] GET / (SERVER)
                 ├─ middleware - query (INTERNAL)
                 ├─ middleware - expressInit (INTERNAL)
                 ├─ middleware - jsonParser (INTERNAL)
                 ├─ middleware - <anonymous> (INTERNAL)
                 └─ request handler - / (INTERNAL)

What's working well

  • W3C Trace Context propagated correctly across all mesh boundaries — Envoy-to-Envoy and Envoy-to-OTel-SDK.
  • Parent-child relationships are correct throughout the entire span tree. The sidecar SERVER span correctly becomes the parent of the app SDK SERVER span.
  • Span kinds correctly applied (SERVER for inbound, CLIENT for outbound) across all Envoy layers.
  • The opentelemetry extension provider defaults to W3C Trace Context (as opposed to B3 used by the legacy Zipkin provider), ensuring modern compatibility.

Opportunities

Improve Envoy span names for human readability — Span names like otel-eval-backend.demo.svc.cluster.local:3000/* and router outbound|3000||otel-eval-backend.demo.svc.cluster.local; egress expose Envoy routing internals. Configurable span name templates (e.g., {method} {service}) would make traces more readable for application developers.
Document trace topology decisions — There is no official documentation explaining when Envoy creates spans, what constitutes a root span, or how the 4-layer topology behaves under retries, circuit breaking, or traffic shifting. Publishing trace modeling guidance would help operators interpret complex traces correctly.

Checklist

  • ✅ W3C Trace Context propagated correctly across all mesh boundaries
  • ✅ Parent-child relationships correct for gateway → sidecar → app chain
  • ✅ Span kinds correctly applied (SERVER for inbound, CLIENT for outbound)
  • ✅ Context propagation works across Envoy-to-Envoy and Envoy-to-SDK boundaries
  • ✅ 100% sampling configurable via Telemetry CR
  • ✅ Traces represent a coherent end-to-end view of request flow
  • ⚠️ Span names are Envoy-internal (see Audience & Signal Quality dimension)
  • ❌ No explicit documentation of trace modeling decisions (when spans are created, what constitutes a root span)
2 Multi-Signal Observability All three signals flowing; trace-log correlation confirmed; metrics lack shared identity with traces/logs ▶

What we observed

All three signals are present and flowing: 37+ unique traces, 275 unique metric names, and 88 access log records. Trace-log correlation is confirmed and working — every ALS log record carries traceId and spanId as native OTLP fields. Verified: log record with traceId=427512ae3f1a5f637ef80f232fb29e0e and spanId=7d5d2a97633c3f5e matches exactly to the Envoy sidecar SERVER span in the trace data, enabling zero-configuration trace-to-log pivoting. Trace-to-metric correlation is not achievable via shared identity: traces use service.name=otel-eval-backend.demo while metrics use service.name=istio-envoy-sidecars. Correlation via k8s.pod.name is possible after collector enrichment but requires operator knowledge of the enrichment pipeline.

What's working well

  • Trace-log correlation is automatic and zero-configuration — every Envoy access log record carries the exact traceId and spanId of the corresponding Envoy span.
  • The Telemetry CR configures both tracing and access logging together, ensuring the two signals are designed as a coherent pair.
  • All three signals are first-class — traces and logs via OTLP push, metrics via Prometheus pull — with no signal requiring a custom adapter or sidecar.

Opportunities

Unify metric identity with trace identity — The service.name in traces (otel-eval-backend.demo) does not match metrics (istio-envoy-sidecars). Adopting workload-based metric resource identity would enable the "pivot from metric alert to trace" workflow that operators expect in OTel-native backends.
Document cross-signal correlation guidance — Istio's documentation does not explain how to correlate metrics with traces (what attributes to join on). Publishing a guide on using k8s.pod.name as the cross-signal join key — and on configuring backends (Grafana, Jaeger, etc.) to leverage trace-log correlation — would significantly improve the operator experience.

Checklist

  • ✅ All three signals are first-class and flowing
  • ✅ Logs carry traceId and spanId enabling trace-log correlation
  • ✅ Trace-log correlation is automatic and verified end-to-end
  • ✅ Signals are designed together (the Telemetry CR configures both tracing and access logging)
  • ❌ Metrics cannot be correlated with traces via service.name — identity is fundamentally different
  • ❌ Mixed collection model (OTLP push for traces/logs, Prometheus pull for metrics) adds operational complexity
  • ❌ No guidance in Istio docs on how to correlate metrics with traces (what attributes to join on)
1 Audience & Signal Quality Envoy-internal span names; unstructured access logs; 70% of metrics are low-level Envoy internals ▶

What we observed

Envoy span names encode internal routing concepts rather than user-meaningful operations: the inbound SERVER span is named otel-eval-backend.demo.svc.cluster.local:3000/* (full Kubernetes DNS FQDN + wildcard path), and the outbound CLIENT span is named router outbound|3000||otel-eval-backend.demo.svc.cluster.local; egress (Envoy cluster routing syntax). Of 275 unique metric names, 193 (~70%) are envoy_* internal counters (circuit breakers, HTTP/2 frame counters, cluster manager internals) while 56 are operationally relevant istio_* metrics. Access logs are unstructured strings with no severity (UNSET for all 88 records), no scope name, and no structured attributes — requiring regex parsing to extract method, path, status code, and latency.

What's working well

  • The istio_* metric family (istio_requests_total, istio_request_duration_milliseconds, istio_request_bytes) is well-designed for RED monitoring with rich source/destination workload, namespace, response code, and security policy dimensions.
  • Trace-log correlation works without customization, enabling operators to jump from a specific span to its access log entry and vice versa.
  • Span kinds are correct, helping trace visualization tools (Jaeger, Tempo, etc.) render the service map and call hierarchy accurately.

Opportunities

Improve Envoy span naming — Implementing configurable span name templates (e.g., {method} {route} for server spans, {method} {service} for client spans) would make traces immediately interpretable by application developers without requiring Istio/Envoy internals knowledge.
Provide metric filtering guidance or defaults — The default collection of all 193 envoy_* metrics creates significant noise. Publishing a recommended metric allowlist for operators (or providing a pre-configured OTel Collector filter pipeline) would help users focus on the 56 operationally relevant istio_* metrics.
Structure access log attributes — Emitting structured log attributes (http.request.method, http.response.status_code, url.path, http.request.duration) alongside or instead of the raw format string — and setting a meaningful SeverityNumber (e.g., ERROR for 5xx, INFO for 2xx) — would transform access logs from a raw dump into a queryable, alertable signal.

Checklist

  • ✅ istio_requests_total, istio_request_duration_milliseconds are user-oriented operational metrics
  • ✅ Span kinds are correct (helps tooling interpret spans)
  • ✅ Trace-log correlation works without customization
  • ❌ Span names expose Envoy routing internals, not logical operations
  • ❌ 193 envoy_* metrics create significant noise; no filtering by default
  • ❌ Access logs are unstructured strings with no severity, no scope, no attributes
  • ❌ No documentation on which metrics are "operational" vs "debug"
  • ❌ Defaults produce high-volume, low-signal telemetry in production
1 Stability & Change Management Telemetry documented; no explicit stability contract; no schemaUrl on OTLP exports; no telemetry changelog ▶

What we observed

Istio has dedicated documentation pages for distributed tracing with OpenTelemetry, metrics (with label definitions for istio_requests_total and related metrics), and access logging. The Telemetry CR API is versioned (telemetry.istio.io/v1) and follows Istio's API stability guarantees. Major telemetry changes (e.g., the migration from EnvoyFilter to the unified Telemetry CR) were documented with migration guidance. However, no schemaUrl is set on any OTLP export from Envoy (traces or logs). Span names and attributes from Envoy can change with Envoy upgrades without explicit notice in Istio release notes. There is no dedicated telemetry changelog section and no explicit policy distinguishing "stable" from "experimental" telemetry fields.

What's working well

  • The Telemetry CR API (telemetry.istio.io/v1) is versioned and documented — operators can rely on the configuration API being stable.
  • The istio_* Prometheus metric schema is de facto stable and documented with label definitions — operators can build dashboards and alerts without fear of breaking changes.
  • Major telemetry migration paths (e.g., EnvoyFilter → Telemetry CR) were communicated over multiple releases with migration guidance.

Opportunities

Add schemaUrl to OTLP trace and log exports — Setting the appropriate OpenTelemetry schema URL on Envoy's OTLP exports would allow backends to correctly interpret attribute versions and automatically migrate deprecated attribute names. This is a low-effort change with significant benefit for tooling compatibility.
Publish an explicit telemetry stability contract — Documenting which telemetry fields are "stable" (guaranteed not to change without notice) vs "experimental" would give operators confidence when building production dashboards and alerts. This could be a simple table in the metrics/tracing reference docs.
Add a dedicated telemetry changelog section to release notes — Span attribute changes from Envoy upgrades are not always called out explicitly in Istio release notes. A dedicated "Telemetry changes" section would help operators proactively update their dashboards, alert rules, and log parsers when upgrading Istio.

Checklist

  • ✅ Telemetry configuration API (Telemetry CR) is versioned and documented
  • ✅ Major telemetry changes communicated with migration guidance
  • ✅ Prometheus metric schema is documented
  • ❌ No schemaUrl on OTLP trace/log exports
  • ❌ No explicit telemetry stability contract separate from API stability
  • ❌ Span names and attributes from Envoy can change with Envoy upgrades without explicit notice
  • ❌ No distinction between "stable" and "experimental" telemetry fields
  • ❌ No dedicated telemetry changelog section in release notes
Key Takeaways

🟢 Strengths

  • Excellent trace-log correlation — Every Envoy access log record carries traceId and spanId as native OTLP fields, enabling zero-configuration trace-log pivoting out of the box.
  • Coherent end-to-end trace topology — The 4-layer span tree (gateway SERVER → gateway CLIENT → sidecar SERVER → app SDK spans) accurately models request flow. W3C Trace Context propagation works correctly across all Envoy-to-Envoy and Envoy-to-SDK boundaries.
  • Clean OTLP integration for traces and logs — The meshConfig.extensionProviders + Telemetry CR configuration model integrates cleanly with standard OTel Collectors. No adapters or custom bridges needed.
  • Rich istio_* operational metrics — istio_requests_total, istio_request_duration_milliseconds, and related metrics provide well-labeled RED metrics directly useful for SLO monitoring and traffic analysis.

🟡 Priority Improvements

  • Migrate Envoy HTTP attributes to current stable semconv — Update from deprecated http.method/http.status_code/http.url to http.request.method/http.response.status_code/url.full. This upstream Envoy change would move Semantic Conventions from Level 1 to Level 2.
  • Unify service identity across signals — Adopt a consistent service.name convention across traces, metrics, and logs. Document the recommended join key (k8s.pod.name) for cross-signal correlation in the interim.
  • Add native OTLP metrics export — An opt-in OTLP metrics exporter alongside Prometheus would unify the integration model and enable metric-to-trace correlation by shared service.name.
  • Structure access logs — Emit structured log attributes (method, path, status code, duration) and a meaningful SeverityNumber to transform access logs from raw strings into a queryable, alertable signal.

🔵 Notable Observations

  • Envoy self-tracing — The Envoy sidecar generates spans for its own outbound calls to the OTel Collector (e.g., otel-collector-opentelemetry-collector.opentelemetry.svc.cluster.local:4318/*) when the collector is inside the mesh. These "meta-spans" appear in trace data and can confuse operators. Istio's documentation does not mention this behavior.
  • Three service.name values for two services — The same backend service appears as otel-eval-backend.demo (Envoy sidecar spans), otel-eval-backend (Node.js SDK spans), and istio-envoy-sidecars (Prometheus metrics) — a significant barrier to unified service-level observability.
  • 275 metrics, 70% Envoy internals — Default metric collection captures all Envoy internal stats (envoy_cluster_http2_*, envoy_cluster_circuit_breakers_*, etc.) alongside the operationally relevant istio_* metrics. Most operators will need to filter this down, but Istio provides no guidance on which metrics to keep.
  • No service.version despite tracking canonical revision — Istio already has istio.canonical_revision on spans and source_canonical_revision on metrics. Mapping this existing data to service.version as a resource attribute would be a low-effort, high-value improvement.
