# Tekton Pipeline — Installation Plan

## Project Overview

**Project:** Tekton Pipeline  
**Version:** v1.12.0 ("Exotic Shorthair Elektrobots LTS")  
**Namespace:** `tekton-pipelines`  
**Install method:** Kubernetes manifests (official release YAML)  
**Cluster:** `kind-otel-eval-tekton`

---

## Step 1: Install Tekton Pipeline

Apply the official release manifest:

```bash
curl -sL "https://infra.tekton.dev/tekton-releases/pipeline/previous/v1.12.0/release.yaml" \
  -o .otel-eval/tekton/tekton/release.yaml

kubectl apply -f .otel-eval/tekton/tekton/release.yaml

kubectl wait --for=condition=Available deployment/tekton-pipelines-controller \
    -n tekton-pipelines --timeout=120s
kubectl wait --for=condition=Available deployment/tekton-pipelines-webhook \
    -n tekton-pipelines --timeout=120s
kubectl wait --for=condition=Available deployment/tekton-events-controller \
    -n tekton-pipelines --timeout=120s
```

**What gets installed:**
- Namespace `tekton-pipelines`
- CRDs: Task, TaskRun, Pipeline, PipelineRun, StepAction, CustomRun
- Deployments: `tekton-pipelines-controller`, `tekton-pipelines-webhook`, `tekton-events-controller`, `tekton-pipelines-remote-resolvers`
- RBAC, ConfigMaps (`config-observability`, `config-tracing`, `config-logging`, etc.)
- ValidatingWebhookConfiguration

## Step 2: Configure Telemetry

### 2a. Enable OTLP HTTP Traces (via `config-tracing`)

> **IMPORTANT:** Tekton v1.12.0 uses **two separate tracing ConfigMaps** that are easy to confuse:
> - `config-observability` — controls metrics protocol and high-level flags (the `_example` section
>   shows `tracing-protocol`/`tracing-endpoint` keys but these are NOT used by the OTLP exporter)
> - `config-tracing` — the actual tracing configuration used by the OTLP HTTP exporter
>
> The controller uses `otlptracehttp` (HTTP, not gRPC). The endpoint must be a full URL
> including scheme and path (e.g., `http://host:4318/v1/traces`).

Patch the `config-tracing` ConfigMap:

```bash
kubectl patch configmap config-tracing \
  -n tekton-pipelines \
  --type merge \
  -p '{
    "data": {
      "enabled": "true",
      "endpoint": "http://otel-collector-opentelemetry-collector.opentelemetry.svc.cluster.local:4318/v1/traces"
    }
  }'
```

The controller watches this ConfigMap and reinitializes the Tracer Provider automatically.
Look for `"message":"initialized Tracer Provider"` in controller logs to confirm.

### 2b. Configure Prometheus Metrics (via `config-observability`)

Tekton defaults to `metrics-protocol: prometheus`, exposing metrics on port 9090.
Update the OTel Collector to scrape these endpoints:

```bash
# Edit .otel-eval/tekton/collector/values.yaml to add prometheus receiver
# Then upgrade the Helm release:
helm upgrade otel-collector open-telemetry/opentelemetry-collector \
    --namespace opentelemetry \
    -f .otel-eval/tekton/collector/values.yaml \
    --wait
```

**Services scraped:**
- `tekton-pipelines-controller.tekton-pipelines.svc.cluster.local:9090`
- `tekton-pipelines-webhook.tekton-pipelines.svc.cluster.local:9090`
- `tekton-events-controller.tekton-pipelines.svc.cluster.local:9090`

## Step 3: Configure Routing

Tekton is not a proxy/gateway — there is no routing to configure for external HTTP traffic.
Traffic is generated by creating Tekton CRD resources (`TaskRun`, `PipelineRun`) that the
controller reconciles and executes as Kubernetes Pods.

## Step 4: Traffic Generation

### Task and Pipeline definitions

```bash
kubectl apply -f .otel-eval/tekton/tekton/traffic/task.yaml
kubectl apply -f .otel-eval/tekton/tekton/traffic/pipeline.yaml
```

### Generate TaskRuns (without trace context)

```bash
for i in $(seq 1 10); do
  kubectl create -f - <<EOF
apiVersion: tekton.dev/v1
kind: TaskRun
metadata:
  name: call-eval-backend-run-${i}
  namespace: default
spec:
  taskRef:
    name: call-eval-backend
  params:
    - name: message
      value: "taskrun-${i}"
EOF
done
```

### Generate TaskRuns (with trace context)

```bash
for i in $(seq 1 5); do
  TRACE_ID=$(cat /dev/urandom | tr -dc 'a-f0-9' | head -c 32)
  SPAN_ID=$(cat /dev/urandom | tr -dc 'a-f0-9' | head -c 16)
  TRACEPARENT="00-${TRACE_ID}-${SPAN_ID}-01"
  kubectl create -f - <<EOF
apiVersion: tekton.dev/v1
kind: TaskRun
metadata:
  name: call-eval-backend-traced-${i}
  namespace: default
  annotations:
    traceparent: "${TRACEPARENT}"
spec:
  taskRef:
    name: call-eval-backend
  params:
    - name: message
      value: "traced-taskrun-${i}"
    - name: traceparent
      value: "${TRACEPARENT}"
EOF
done
```

### Generate PipelineRuns

```bash
for i in $(seq 1 5); do
  kubectl create -f - <<EOF
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  name: eval-pipeline-run-${i}
  namespace: default
spec:
  pipelineRef:
    name: eval-pipeline
EOF
done
```

## Telemetry Summary

| Signal  | Protocol        | Source                                    | Notes                                                          |
|---------|-----------------|-------------------------------------------|----------------------------------------------------------------|
| Traces  | OTLP HTTP       | `tekton-pipelines-controller` pod         | TaskRun/PipelineRun reconcile lifecycle spans                  |
| Metrics | Prometheus      | `:9090` on controller/webhook/events pods | Scraped by OTel Collector prometheus receiver                  |
| Logs    | stdout (JSON)   | Pod logs only                             | No OTLP log export; structured JSON via zap logger             |

### Trace service names
- `taskrun-reconciler` — spans for TaskRun reconciliation
- `pipelinerun-reconciler` — spans for PipelineRun reconciliation

### Key span names
`TaskRunReconciler`, `TaskRun:ReconcileKind`, `PipelineRun:ReconcileKind`, `prepare`, `createPod`, `reconcile`, `resolvePipelineState`, `runNextSchedulableTask`, `createTaskRun`, `stopSidecars`, `finishReconcileUpdateEmitEvents`, `durationAndCountMetrics`

### Key Prometheus metrics
- `tekton_pipelines_controller_taskrun_duration_seconds` (histogram)
- `tekton_pipelines_controller_pipelinerun_duration_seconds` (histogram)
- `tekton_pipelines_controller_taskrun_total` (counter)
- `tekton_pipelines_controller_pipelinerun_total` (counter)
- `tekton_pipelines_controller_running_taskruns` (gauge)
- `tekton_pipelines_controller_running_pipelineruns` (gauge)
- `tekton_pipelines_controller_taskruns_pod_latency_milliseconds` (histogram)
- `tekton_pipelines_controller_pipelinerun_taskrun_duration_seconds` (histogram)

## Known Issues / Gotchas

1. **Two tracing ConfigMaps**: `config-observability` and `config-tracing` serve different purposes.
   The `_example` section of `config-observability` shows `tracing-protocol`/`tracing-endpoint` keys
   that appear functional but are NOT used by the OTLP exporter in the controller binary.

2. **OTLP HTTP only**: Despite `config-observability` showing `grpc` as a protocol option,
   the actual tracing implementation (`pkg/tracing/tracing.go`) uses `otlptracehttp` exclusively.
   The endpoint must use HTTP format: `http://host:port/v1/traces`.

3. **Controller restart required**: After the OTel Collector is restarted (e.g., after a Helm upgrade),
   the Tekton controller must be restarted to re-establish the OTLP HTTP connection.

4. **No OTLP log export**: Tekton has no mechanism to export logs via OTLP. Logs are only
   available via stdout/stderr of the controller pods.
